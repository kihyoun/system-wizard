# GitLab을 기본으로 사용하고 선택적으로 GitHub 코드 미러 사용하기

보호 장치가 있는 백업 도우미는 보호된 GitLab 기본 브랜치의 커밋을 명시적으로 매핑한
GitHub 브랜치로 전달합니다. 명시적으로 선택하는 기능입니다. 체크아웃에 도우미를 추가해도
원격 저장소를 변경하거나, 동기화를 활성화하거나, 프로젝트 메타데이터를 마이그레이션하지
않습니다. 활성화 전에 기본 저장소를 선택하고 선택한 CI 구성에 도우미를 통합하세요.

## 개발 및 추적 역할

System과 Wizard용 GitLab 프로젝트와 중앙 이슈 트래커를 선택하세요. 운영자는 이슈를
System 프로젝트에 모으면서 Wizard 변경은 Wizard 프로젝트에서 검토할 수 있습니다.
선택한 식별 정보는 에이전트 지침과 외부 프로젝트 추적에 기록하세요. 제품은 특정 관리자의
GitLab 호스트나 이슈 이력을 요구하지 않습니다.

활성화 후에는 해당 GitLab 트래커에 작업을 만들고, 의도한 GitLab 기본 브랜치에서 브랜치를
만든 뒤, 영향을 받는 소스 프로젝트에서 병합 요청을 여세요. 프로젝트 간 이슈는 프로젝트가
명시된 GitLab 참조로 연결하세요. 프로젝트의 필수 검사를 실행하고 최종 차이를 검토한 뒤
그곳에서 병합하세요. 그러면 보호된 기본 브랜치 파이프라인이 정확히 그 병합 커밋을 매핑된
GitHub 브랜치로 전달합니다. GitHub는 공개 코드 미러이며 두 번째 병합 대상이 아닙니다.
기여자와 에이전트는 같은 이슈, 브랜치, 검토, 병합 절차를 사용합니다.

GitHub 가용성은 소스 검사, 병합 요청 작업, 비공개 전달의 사전 조건이 아닙니다. 활성화된
미러 작업이 실패하면 파이프라인에 실패가 명확히 남고 작업을 재시도할 수 있습니다. 필수 소스
검사 증거와 전달 증거는 계속 독립적으로 사용할 수 있습니다. `allow_failure`로 미러 실패를
숨기거나, 내부 작업을 계속하기 전에 해당 작업의 성공을 요구하지 마세요. 그에 맞게 병합
권한과 필수 소스 검사를 구성하세요.

미러 작업 성공은 운영 환경을 승격하지 않습니다. 특히 Wizard 운영 환경은 검증된
파이프라인, 소스, 불변 이미지 증거를 사용하는 별도의 명시적 작업으로 유지됩니다.
개발 위치를 옮긴다고 Wizard의 기존 배포 메커니즘이 전체 플랫폼 자동 배포로 확장되지는
않습니다.

## 활성화 전에 이력 정리

System과 Wizard 양쪽의 명시적 매핑을 기록하세요.

| 설정 | 의미 |
| --- | --- |
| 소스 프로젝트 | 정확한 GitLab `owner/project` 식별 정보 |
| 소스 브랜치 | 프로젝트의 보호된 GitLab 기본 브랜치 |
| 백업 저장소 | 기존 `git@github.com:owner/repository.git` |
| 백업 브랜치 | 명시적인 대상이며 소스 브랜치와 이름이 같을 필요는 없음 |

관리형 소스 가져오기 절차로 초기화한 Wizard는 업스트림 GitHub 계보가 아닌 스캐폴드/가져오기
커밋으로 시작합니다. 이런 저장소는 기존 업스트림 브랜치를 단순히 fast-forward할 수 없습니다.
이력을 보존하며 GitLab으로 마이그레이션하거나, 합의된 시작점을 가진 별도 백업 브랜치를
검토하세요. 모든 소스와 대상 쌍에 같은 계보 검사를 적용합니다. 강제 푸시, 자동 병합 생성,
백업 대상의 은밀한 전환을 하지 마세요. 도우미는 호환되는 계보를 가진 기존 대상 브랜치를
요구합니다.

### 소스 프로젝트와 관리형 전달 프로젝트

관리형 Wizard 저장소에 독립적인 비공개 이력이 있다면, 깨끗한 소스 우선 프로젝트가 공개
소스 계보를 보존하는 동안 기존 관리형 저장소는 계속 애플리케이션을 빌드하고 전달할 수
있습니다. 두 프로젝트가 같은 GitLab에 있어도 역할은 구분됩니다. 관리형 전달 이력은
비공개로 유지하세요. 그 조상을 공개 소스 브랜치에 병합하면 결과 파일이 같아 보이더라도
해당 커밋도 공개됩니다. 깨끗한 소스 프로젝트를 만들 때 기존 프로젝트, 참조, 기록,
관리형 레시피, 배포 세대 하한을 유지하세요.

소스에서 전달로의 인계는 명시적이며 검토를 거칩니다. 승인된 병합 `sourceCommit`에 대해
필수 `build:source`와 `test:browser` 작업이 정확히 그 SHA에서 성공했는지 검증하세요.
해당 작업 식별 정보, 소스 SHA, 현재 전달 기준점, 결과 `deliveryCommit`을 외부 추적이나
비공개 운영자 기록에 기록하세요. 전체 파이프라인 성공이 소스 게이트는 아닙니다. 선택적
GitHub 미러 장애로 필수 작업은 성공했어도 파이프라인이 실패할 수 있습니다. 비공개 전달
빌드, 테스트, 검토된 인계에는 GitHub 읽기나 미러 작업 성공이 필요하지 않습니다.

해당 소스 커밋에서 검토된 애플리케이션 변경만 전송하고, 다른 대상 파일을 검사한 뒤,
대상의 정상 브랜치/MR 절차나 보호된 관리형 작업을 사용하세요. 충돌을 우회하려고 전체
소스 트리를 다시 가져와 관리형 CI, 소유권 마커, 이력을 대체하지 마세요. 전송된 파일을
선택한 소스 리비전과 대조하고 전달 빌드와 브라우저 테스트를 실행하세요. 운영 환경 증거는
실제 전달 커밋과 이미지 다이제스트를 식별하며, 인계 매핑이 이를 검토된 소스 커밋에 연결합니다.
이 절차는 자동 소스-전달 동기화나 자동 System 배포를 의미하지 않습니다.

업스트림 공개 서브모듈 URL은 이식 가능하게 유지하세요. GitLab을 기본으로 사용하는
System 체크아웃 안에서는 업데이트 전에 일치하는 비공개 Wizard 소스를 명시적으로 선택하세요.

```sh
git config submodule.wizard.url '<operator-selected GitLab Wizard clone URL>'
git submodule update --init wizard
```

자격 증명이 삽입되지 않은 인증된 복제 URL을 사용하세요. `git submodule
sync`는 로컬 재정의를 `.gitmodules` 값으로 대체하므로 동기화가 필요하면 비공개 매핑을 다시
적용하세요. System CI에서 `prepare:wizard-source`는 `GIT_SUBMODULE_STRATEGY: none`으로
Runner의 자동 서브모듈 체크아웃을 비활성화합니다. 이어서 `gitlab/prepare-wizard-source.js`가
소스 패키징 전에 구성된 비공개 선택자로 정확한 gitlink를 초기화하고 검증합니다. 이 준비 단계
후에만 재정의를 적용하면 너무 늦습니다. 선택한 Wizard 저장소에 정확한 System gitlink가
있는지 확인하세요. 개발과 테스트가 진행되기 위해 GitHub 읽기의 성공이 필요해서는 안 됩니다.

## 도우미 계약

`gitlab/github-backup.sh`는 의도한 기본 GitLab 프로젝트를 가리키는 `origin`이 있는
체크아웃에서 실행됩니다. CI 통합은 고정된 Node 24 런타임, Git, OpenSSH 클라이언트/에이전트,
`mkdir`와 `rmdir`가 있는 POSIX 셸을 제공합니다. 동반 파일 `github-backup-transport.js`를
셸 도우미 옆에 두세요. 구성은 보호된 CI 작업에서 옵니다.

| 변수 | 필수 값 |
| --- | --- |
| `GITHUB_BACKUP_ENABLED` | 구성된 백업 작업을 명시적으로 활성화하려면 `true` |
| `GITHUB_BACKUP_SOURCE_PROJECT` | 승인된 정확한 `CI_PROJECT_PATH` |
| `GITHUB_BACKUP_REMOTE` | 자격 증명 없는 승인된 GitHub SSH 저장소 |
| `GITHUB_BACKUP_BRANCH` | 승인된 기존 백업 브랜치 |
| `GITHUB_BACKUP_TIMEOUT_SECONDS` | 선택적 전송별 기한이며 정수 1~300, 기본값 30 |
| `GITHUB_SSH_KNOWN_HOSTS` | 독립적으로 검증한 GitHub SSH 호스트 키가 들어 있는 보호 파일 변수 |

GitLab은 `GITLAB_CI`, `CI_PIPELINE_SOURCE`, `CI_PROJECT_PATH`, `CI_DEFAULT_BRANCH`,
`CI_COMMIT_BRANCH`, `CI_COMMIT_REF_PROTECTED`, `CI_COMMIT_SHA`를 제공합니다. 보호된
기본 브랜치의 **푸시** 파이프라인만 대상입니다. MR, API, 수동/웹, 태그 파이프라인은 복제하지
않습니다. 체크아웃은 전체 고정 SHA와 일치해야 하고, 해당 커밋은 새로 가져온 소스 기본
브랜치에 여전히 속해야 합니다. 검토된 병합만 도달하도록 보호 브랜치 권한을 구성하세요.
셸 스크립트는 검토가 이루어졌다는 사실을 입증할 수 없습니다.

도우미는 CI 복제의 얕은 이력 해제를 포함해 완전한 소스 계보를 가져옵니다. 따라서 Runner에는
기본 저장소 읽기 접근과 매핑된 백업 쓰기 접근이 필요합니다. `origin`, 체크아웃, 로컬 브랜치는
변경하지 않습니다. `refs/system-backup/` 아래의 임시 참조는 정상 종료/시그널 시 제거됩니다.
이 임시 참조는 대체 가능하지만 대상 브랜치는 절대 강제 푸시하지 않습니다.

각 호출은 정상 Git 푸시로 **동일한 병합 커밋**을 전달합니다.

- 대상이 고정 커밋보다 뒤처지면 fast-forward로만 진행합니다.
- 대상이 같으면 멱등적인 성공입니다.
- 대상이 대기열의 더 오래된 커밋을 이미 포함하면 되돌리지 않고 성공합니다.
- 대상이 분기되었거나, 브랜치가 없거나, 소스 커밋이 제거되었으면 실패를 명확히 표시합니다.
- 거부된 푸시와 불확실한 응답은 다시 가져와 재평가하며, 푸시는 최대 세 번 시도합니다.
  접근 오류를 해결한 뒤 CI 작업을 재시도하세요.

푸시는 상속된 `push.followTags`를 명시적으로 비활성화하며 구성된 브랜치만 전달합니다.
각 가져오기/푸시는 실제 경과 시간 기한이 있는 Node 전송 경계 안에서 실행됩니다. Unix에서는
프로세스 그룹을 소유하고 TERM을 보낸 뒤, 선두 프로세스가 먼저 종료되었어도 2초 후 KILL을
보냅니다. Windows 오프라인 픽스처는 `taskkill`로 자신이 기록한 자식 PID/트리만 대상으로
합니다. 취소도 같은 트리 정리를 사용합니다. CI 작업은 외부 안전 경계로 유한한 작업 시간
제한과 Runner 프로세스 정리를 유지해야 합니다. 기한 실패는 체크아웃 잠금을 해제하지만,
가로챌 수 없는 호스트/프로세스 종료에는 여전히 아래의 중단된 소유자 검사가 필요합니다.

체크아웃 로컬 잠금은 같은 Git 객체 데이터베이스를 사용하는 중첩 호출을 거부합니다.
가로챌 수 없는 종료는 잠금을 남길 수 있습니다. `.git/system-github-backup.lock`을
제거하기 전에 소유자를 검사하세요. 연결된 작업 트리에서는 공통 Git 디렉터리를 사용하세요.
**분산 잠금이 아닙니다.** CI 작업은 대상 파이프라인 전체에서 저장소별로 동일한
`resource_group`도 사용해야 합니다. 독립된 두 체크아웃이 경합해도 정상 Git 참조 갱신은
원자적입니다. 더 오래된 작업이 최신 작업 뒤에 실행되어도 안전합니다.
[GitLab 자원 그룹](https://docs.gitlab.com/ci/resource_groups/)을 참조하세요.

도우미는 전송 출력을 숨기고 셸 추적과 로컬 Git 훅을 비활성화하며 고정된 결과 메시지만
기록합니다. 전송 출력은 버리고, 터미널/자격 증명 관리자 프롬프트를 비활성화하며, SSH는
BatchMode와 엄격한 호스트 키 검사를 사용합니다. 작업은 검증된 `known_hosts`를 미리
프로비저닝해야 합니다. 알 수 없는 키는 프롬프트나 검증 우회 대신 실패합니다. 핵심 도우미는
개인 키 변수를 읽거나 원격 URL을 출력하거나 자격 증명을 설치하지 않습니다. CI 래퍼가
선택한 개인 키를 읽고 자신이 소유한 임시 SSH 에이전트를 시작합니다. 이 설정에는
보호/마스킹된 자격 증명과 검증된 호스트 키를 사용해야 합니다. 주변 명령에서 CI 디버그
추적을 활성화하거나 비밀 정보를 출력하지 마세요. 별도로 허가되지 않으면 기존 보호
`GITHUB_SSH_PRIVATE_KEY` 식별 정보를 유지하세요.

## 선택한 CI 구성과 통합

System의 `deploy:github` 작업은 필수 검사 후 이 도우미를 사용합니다. 명시적 선택
기능이며 선택된 기본 브랜치, 지원되는 고정 Node 런타임, 검증된 `GITHUB_SSH_KNOWN_HOSTS`
파일, 기존 보호 SSH 식별 정보를 사용합니다. 활성화 전에 매핑된 값을 모두 구성하세요.
작업은 `github-backup-$CI_PROJECT_ID`로 직렬화되며 실패는 파이프라인 실패 결과로 남습니다.

System의 `build` 작업은 필수 런타임 검사 후 독립형 런타임 기반 이미지를 자체 GitLab
Registry에 `$CI_REGISTRY_IMAGE:$CI_COMMIT_REF_SLUG`로 게시합니다. 완전한 후속 컨트롤러는
후보 승인 작업이 같은 프로젝트의 `/successor` 저장소에 불변 다이제스트 및 승인 증거와 함께
별도로 게시합니다. 완전한 이미지의 배포는
[후속 세대 승격 안내](../bootstrapper/README.md#promoting-a-tested-successor-controller)를 따르세요.
어느 게시도 Docker Hub 게시 자격 증명을 요구하거나, 운영 환경 승격을 활성화하거나,
자원을 많이 사용하는 System 후보 검사를 우회하지 않습니다. GitHub 미러링은 계속 독립적인
명시적 선택 기능입니다.

레거시 관리형 Wizard는 빌드/테스트와 설치된 선택적 환경 작업에
`.system-bootstrapper/ci.yml`을 선택합니다. 보존된 업스트림 `.gitlab-ci.yml`은 활성화되지
않습니다. 소스 우선 저장소는 대신 커밋된 `.gitlab/primary.yml`을 사용합니다.
항상 `build:source`(잠금 설치, 린트, 단위 테스트, TypeScript, 프로덕션 빌드, 구성 내보내기
번들)와, 정확히 그 빌드 아티팩트를 Playwright Chromium 및 루프백 미리 보기로 검사하는
`test:browser`를 실행합니다. 이 두 소스 검사는 호스트 Docker 접근이 필요하지 않습니다.

`WIZARD_DELIVERY_ENABLED=true`이면 같은 소스 우선 파이프라인이 커밋된 일반 빌드
레시피로 필수 `build:wizard`와 `test:wizard` 작업도 실행합니다. 이 작업에는 신뢰할 수 있는
Docker Runner가 필요하며, 불변 이미지를 같은 프로젝트의 Registry에 게시하고 정확히 그
이미지를 검증합니다. 구성된 선택적 Review/Beta 작업도 같은 프로젝트를 사용합니다.
운영 환경은 별도의 제어된 승격으로 유지됩니다. 기존 관리형 전달 프로젝트를 교체할 때는
[소스 우선 채택 안내](../project-bootstrap/wizard-source-primary/README.md)를 따르세요.
라이브 의존성과 필수 복구 데이터를 마이그레이션할 때까지 이전 프로젝트를 삭제하지 마세요.

별도 소스 및 전달 프로젝트를 유지하는 설치에서는 이 플래그를 설정하지 않아도 됩니다.
비공개 전달 프로젝트의 관리형 CI 경로와 레시피를 유지하세요. 레거시 게시 작업을 얻기 위해
보존된 업스트림 파이프라인을 활성화하지 마세요.

자격을 갖춘 보호된 기본 브랜치 파이프라인만 `deploy:github`에 도달합니다. 게시자는 보호된
활성화 게이트, 직렬화된 자원 그룹, 명확한 실패 결과를 유지합니다. 소스 우선 전달은 모든
필수 기본 소스/이미지 검사를 독립적으로 검증합니다. 공개 미러만 대기, 실행, 실패, 취소
상태인 것은 비공개 환경이나 운영 환경 승격을 막지 않습니다. 소스 병합은 여전히 프로젝트의
파이프라인 성공 및 토론 게이트를 준수합니다.

기존 보호 `GITHUB_SSH_PRIVATE_KEY` 식별 정보를 사용하세요. 파일 변수를 권장하며,
기존 마스킹된 여러 줄 값도 계속 지원합니다. SSH 호스트 키는 실행 시 키 스캔이 아니라
독립적인 검증 후 `GITHUB_SSH_KNOWN_HOSTS`에 제공하세요. System CI는
`WIZARD_PRIMARY_REPOSITORY_URL`을 사용해 `CI_SERVER_URL`과 같은 HTTPS 원본 주소에
있는 운영자 선택 Wizard 프로젝트에서 작업 토큰으로 정확한 gitlink를 가져올 수 있습니다.
GitLab의 작업 토큰 권한으로 System 프로젝트가 해당 Wizard 프로젝트를 읽을 수 있도록
허가하세요. URL은 비밀이 아닌 선택자이며 일반 MR 파이프라인에서도 사용할 수 있어야 합니다.
이 변수만 보호하면 해당 파이프라인이 공개 대체 경로에 남게 됩니다. 작업 토큰은 프로세스
내부에만 유지하고 리디렉션은 거부합니다. 공개 `.gitmodules` 매핑은 새로운 공개 재귀
체크아웃을 위해 계속 사용할 수 있습니다. 가져오기 전에 소스 선택자는 기존 또는 재초기화된
Wizard 서브모듈의 캐시된 `remote.origin.url`을 선택한 자격 증명 없는 내부 URL로 조정한 뒤
정확한 gitlink를 검증합니다. 따라서 이전에 캐시된 공개 원격 주소가 선택된 내부 소스를
몰래 무시할 수 없습니다. System 상위 프로젝트의 `origin`은 변경하지 않습니다.

업스트림 Wizard에는 System gitlink를 갱신하고 레거시 고정 GitLab 호스트를 사용하는
`deploy:system`도 있습니다. 무작정 다시 활성화하지 마세요. 내부 순서는 Wizard 병합/검사와
GitLab 소스 프로젝트에서의 정확한 커밋 가용성 확인, 그다음 정상 검토 절차를 통한 명시적인
System gitlink 갱신과 System 검사입니다. 공개 미러링에는 별도의 복원 순서가 있습니다.
System 미러가 새로운 공개 재귀 체크아웃을 지원한다고 보고하기 전에 참조하는 Wizard
커밋이 GitHub 미러에 있는지 확인하세요. 공개 미러의 지연은 내부 gitlink 작업이나 비공개
전달을 차단하지 않습니다. 자동 System 병합이나 운영 환경 배포는 도입하지 않습니다.
운영 환경은 운영자가 확인하는 명시적인
[승격 작업](../project-bootstrap/wizard-production/README.md)으로 유지됩니다.

### 하나의 System 릴리스로 Wizard 전달

명시적으로 선택하는 대안은 인터페이스와 System 변경을 하나의 System 병합 요청에 묶는
것입니다. 검토된 Wizard 커밋을 전용 소스 참조에 유지하고, System MR에 정확한 gitlink를
고정하며, 검토에 전체 비교를 포함하세요. 이는 Wizard 기본 브랜치를 진행시키거나 기본
Wizard 파이프라인 증거를 만들어 내지 않습니다. System 파이프라인이 Wizard 소스 및
브라우저 검사, 전체 플랫폼 승인 검사, 두 이미지 게시를 함께 실행합니다. 병합된 기본
브랜치는 필수 검사를 별도로 받습니다. 이 경로에는 중간 System 파이프라인이나 두 번째
Wizard 파이프라인이 필요하지 않습니다.

공개 재귀 체크아웃을 위해 일반 GitHub 미러 구성에 더해 다음 **보호된** System CI 변수를
활성화하세요.

| 변수 | 값 |
| --- | --- |
| `WIZARD_GITHUB_SOURCE_PUBLISH_ENABLED` | System 미러 전에 정확한 의존성을 게시하려면 `true` |
| `WIZARD_GITHUB_BACKUP_REMOTE` | 커밋된 Wizard `.gitmodules` HTTPS URL과 일치하는 GitHub SSH 대상 |
| `WIZARD_GITHUB_SSH_PRIVATE_KEY` | 허가된 Wizard 저장소 게시 식별 정보가 있는 파일 변수 |

Wizard 저장소의 허가된 게시 식별 정보를 사용하세요. System 배포 키가 다른 저장소 접근을
의미하지는 않습니다. 기존의 독립적으로 검증한 GitHub 호스트 키 파일이 해당 대상에도
적용되어야 합니다. 래퍼는 두 식별 정보를 분리해 유지하며 종료 시 비공개 사본과 SSH
에이전트를 제거합니다.

`gitlab/publish-wizard-source.js`는 보호된 System 기본 브랜치 푸시에서 정확한 gitlink를
읽고, 작업 토큰으로 같은 인스턴스의 정식 Wizard 소스에서 이를 얻어
`system-release/<Wizard commit>`을 게시합니다. 원자적인 생성 전용 임대는 조상을 포함해
기존 참조의 변경을 거부합니다. 재시도는 같은 커밋을 검증합니다. 도우미는 일반 System
미러를 실행하기 전에 공개 HTTPS 저장소에서 정확히 그 참조를 익명으로 가져옵니다.
어느 Wizard 기본 브랜치도 변경하지 않습니다. 게시된 릴리스나 복구 입력이 필요로 하는 동안
이 소스 참조를 유지하세요.

같은 파이프라인의 `test-results/github/wizard-source.json` 기록은 소스, 대상, 작업 식별
정보만 기록합니다. 명시적으로 선택하는
[쌍 릴리스 업데이트 도구](../bootstrapper/README.md#deliberately-updating-the-accepted-controller-and-wizard-together)는
이 성공한 게시 증거, 전체 승인된 System 파이프라인, 변경 없는 Docker Hub 이미지 쌍
아티팩트를 요구합니다. 기본 컨트롤러 전용 모드는 원래 미러 정책을 유지합니다.
운영 환경 승격은 계속 명시적이며, 소스 우선 Wizard 연결과 일반 기본 승격 규칙은 별도로
그대로 유지됩니다.

## 선택한 기본/백업 관계 활성화

1. 역할을 바꾸기 전에 자체 인프라에서 실제 GitLab 검토, 필수 검사, 배포 절차를 검증하세요.
2. 매핑에 합의하고 위의 이력 사전 조건을 해결하세요. 이전 참조를 보존하고 롤백 연락처/절차를
   기록하세요. 전환 중 경합하는 쓰기를 일시 중지하세요. GitHub는 백업 전용이 되며 또 다른
   병합 대상이 아닙니다.
3. GitHub Actions, 배포, 웹훅, 역방향 미러를 감사하세요. 활성화 **전에** 백업 푸시에 대한
   반응을 비활성화하거나 명시적으로 격리하세요. 바이트가 동일한 커밋에 새 건너뛰기 마커를
   추가하려면 식별 정보가 바뀝니다. 되돌아오는 루프를 막도록 Wizard에서 System으로 가는
   작업은 별도로 감사하세요.
4. 원격 저장소, 에이전트 안내, 이슈/MR 처리를 새 기본 위치로 명시적으로 갱신하세요.
   아래 절차로 진행 중인 작업을 전송하세요. Git 푸시는 이슈 메타데이터를 옮기지 않습니다.
   이슈 마이그레이션은 이 도우미와 별개입니다.
5. 허가된 자격 증명과 검증된 known-host 자료로 의도한 보호 백업 작업만 검토하고 활성화하세요.
   명시적으로 제어되는 통합 검사 전에 오프라인 회귀 검사를 실행하세요.
6. 검토된 절차로 무해한 GitLab 변경을 병합하세요. GitHub의 결과 SHA가 정확히 같은지
   비교하고, 명확한 실패/재시도를 테스트하며, 역방향 푸시나 의도하지 않은 배포가 없었는지
   검증하세요. 폐기 가능한 복원 연습이 통과할 때까지 이전 절차를 복구 가능하게 유지하세요.

## 출처를 잃지 않고 진행 중인 작업 전송

트래커를 바꾸기 전에 진행 중인 이슈와 pull request 목록을 만드세요. 원래 저장소 식별 정보,
항목 유형/번호, URL, 제목, 설명, 상태, 레이블, 소유권, 타임스탬프, 관련 토론, 승인 기준을
포함하세요. 목록, 이전-새 식별자 매핑, 전환 검증은 소스 문서가 아닌 외부 추적이나 비공개
운영자 기록에 보관하세요. 이슈 내보내기에 토큰, 비공개 로그, 배포 자격 증명을 절대 포함하지
마세요.

각 진행 중인 이슈는 대체 항목을 만들기 전에 대상에서 정확한 원래 URL을 검색하세요.
새 항목 설명에 해당 URL과 원래 식별 정보를 넣고 요구 사항을 보존하세요. 복사한 댓글은
가져온 사람의 새 발언처럼 제시하지 말고 원래 작성자와 타임스탬프를 표시하세요. 결과 텍스트와
링크를 검증하세요. 옮김으로 종료하기 전에 기존 항목에 대상 URL을 다시 기록하세요.
중단된 전송이 중복을 만들지 않도록 기록된 매핑과 소스 식별 정보로 재시도하세요.

종료된 과거 토론은 이전 트래커에서 계속 읽을 수 있도록 남겨 둘 수 있습니다. 이 선택을
명시적으로 기록하세요. Git 소스 미러는 해당 이력을 마이그레이션하지 않습니다. 이전 서비스
없이도 기록에 접근해야 한다면 운영자 내보내기를 보관하세요. 이미 병합된 커밋과 과거 커밋
메시지의 이전 이슈 참조를 바꾸기 위해 다시 쓸 필요는 없습니다. 새 토론은 선택한 GitLab
트래커를 사용합니다. 지원된다면 미러에서 새 이슈 생성과 경합하는 병합 경로를 비활성화하고,
새 기여 대상을 외부에 게시하세요.

열린 pull request를 GitLab 병합 요청으로 다시 만들기 전에는 브랜치, 대상, 검토 상태를
별도로 확인해야 합니다. 원래 검토는 과거 맥락이며 바뀐 차이에 대한 새 승인이 아닙니다.
관리형 파일을 덮어쓰거나 대상의 기존 이력을 다시 쓰는 방식으로 브랜치를 가져오지 마세요.

## 운영자 소유 인프라에서 전환 검증

각 소스 프로젝트에 무해한 변경과 비공개 검증 기록을 사용하세요.

1. 고유 마커가 있는 GitLab 이슈를 만드세요. 이를 참조하는 브랜치와 병합 요청을 만드세요.
   Wizard에서는 프로젝트 간 중앙 이슈 링크를 검증하세요. 에이전트가 이슈를 읽고 병합
   요청을 제출/검토할 수 있는지 확인하세요.
2. MR 파이프라인이 코드 미러를 게시할 수 없고 필수 검사 실패가 병합/전달 게이트를 통과할
   수 없음을 입증하세요. 수정된 차이를 보호 브랜치의 의도한 권한으로 검토하고 병합하세요.
3. 결과 전체 GitLab 커밋 SHA를 기록하세요. 해당 기본 브랜치 파이프라인이 성공하고,
   합성 병합 커밋, 역방향 푸시, 운영 환경 변경 없이 GitHub에 정확히 그 커밋이 있는지
   확인하세요. 대기 중인 새 병합이 없을 때 최종 브랜치 끝을 비교하세요. 대기열의 오래된
   작업은 자신의 커밋을 이미 포함한 대상을 되돌리면 안 됩니다.
4. 미러 작업을 다시 실행해 멱등성을 입증하세요. 전용 테스트 자격 증명과 격리된 매핑에서
   쓰기 접근 거부를 실행하고 명확한 실패를 확인한 뒤, 접근을 복원하고 재시도하세요.
   이 테스트를 위해 공유 운영 환경 키를 망가뜨리거나 공개 브랜치에 분기된 이력을 만들어
   내지 마세요.
5. System에서는 내부 서브모듈 매핑으로 GitLab 기본 체크아웃을 검증하세요. 전체 파이프라인
   성공 대신 성공한 정확한 필수 작업 증거로, GitHub를 사용할 수 없어도 필수 작업과 비공개
   Wizard 전달이 실행될 수 있는지 확인하세요. 활성화된 미러 작업은 재시도할 때까지 명확한
   실패로 남습니다. 참조된 Wizard 커밋이 미러링된 후에는 공개 System 미러가 복원 준비가
   되었다고 보고하기 전에 새로운 공개 재귀 체크아웃을 별도로 검증하세요.
6. 기존 복구 계약으로 완료된 Harvest와 일치하는 구성 내보내기를 확보하세요. 폐기 가능한
   복원에서 픽스처 사용자, 저장소 HEAD, 이슈 설명 마커, 초안 MR/토론 메타데이터,
   암호화된 CI 설정을 검증한 다음 Runner 작업을 실행하세요. 복구된 상태와 매핑을 검토할
   때까지 복원된 미러 쓰기는 비활성화하세요.

커밋된 콜드 복구 시나리오는 사용자, 저장소/이슈 식별 정보, 암호화된 CI 변수, Registry
데이터에 더해 소스 브랜치와 토론 및 답글이 있는 초안 MR을 만듭니다. 복원 후 정확한 소스
커밋, MR 식별 정보, 제목, 설명, 상태, 작성자, 생성 시간과 두 메모의 식별 정보, 텍스트,
작성자, 타임스탬프, 해결 상태를 확인합니다. 이슈 검사는 제목이나 상태가 아닌 설명 마커를
비교합니다. MR은 병합 커밋/시간 필드가 null인 열린 상태로 유지되므로, 이미 병합된 MR의
복원을 입증하는 것은 아닙니다. 픽스처는 기본 브랜치를 변경하지 않습니다. 오프라인 계약
성공만으로 실제 콜드 복원 통과, 라이브 전환, 성공적인 운영 환경 배포가 성립하지 않습니다.
충분한 용량에서 [폐기 가능한 복구 시나리오](../tests/e2e/README.md)를 실행하세요.

## 범위와 복원 제한

도우미는 구성된 브랜치 하나와 도달 가능한 Git 객체를 백업합니다. 태그, 다른 브랜치, 삭제,
Git LFS 데이터, 서브모듈 저장소는 미러링하지 않습니다. 더 넓은 범위를 주장하기 전에
해당 정책을 명시적으로 정의하세요. 이슈, MR, 토론, 사용자, CI 비밀 정보, Registry 이미지,
아티팩트, 서비스 구성은 백업하지 않습니다.

플랫폼의 기존 [영구 볼륨](PERSISTENT_VOLUME.md)과
[콜드 Harvest/Seed 복구](RECOVERY_CONTRACT.md)는 이 코드 미러와 별도로 서비스 상태를
처리합니다. GitLab의 보존된 `config`와 `data` 트리에는 구성/비밀 정보, 데이터베이스,
저장소, 로컬 Registry/아티팩트 데이터가 포함됩니다. 이슈, MR 토론, 사용자, CI 설정은
Git 커밋뿐 아니라 해당 GitLab 상태에 의존합니다. Harvest는 GitLab이 정상 중지된 동안
이 트리를 캡처하고, 별도 Wizard 구성 내보내기가 Bootstrapper 설정을 제공합니다.
보존된 라이브 볼륨은 더 오래된 Seed를 적용하지 않고도 재사용할 수 있습니다.

GitLab을 기본으로 선택한다고 두 번째 백업 서비스가 필요하지는 않습니다. 운영자가 구성한
외부 객체 저장소가 있다면 Seed의 실제 로컬 범위와 비교해 검토하세요. 비밀 자료를 보호하고
복구 계약이 요구하는 일치 버전/에디션과 이미지 식별 정보를 보존하세요. 설치의
[백업 범위](https://docs.gitlab.com/administration/backup_restore/backup_gitlab/)와
[복원 사전 조건](https://docs.gitlab.com/administration/backup_restore/restore_gitlab/)을 검토한 뒤
격리된 폐기 가능 시스템에서 연습하세요. 브랜치 전달 도우미는 Harvest/Seed나 GitLab 기본
백업/복원 작업을 실행하지 않습니다.

## 오프라인 회귀 검사

`node tests/gitlab/github-backup.js`를 Git과 POSIX `sh`를 사용할 수 있는 곳에서 실행하세요.
Windows에서는 `GITHUB_BACKUP_TEST_SHELL`을 Git for Windows의 `usr/bin/sh.exe`로
설정하세요. 픽스처는 자신이 소유한 임시 로컬 저장소만 생성하고 제거합니다.
`GITHUB_BACKUP_OFFLINE_FIXTURE=1`은 GitHub SSH 대신 기존의 절대 경로 로컬 bare 대상을
허용합니다. 이 옵션은 해당 오프라인 픽스처 전용이며 운영 환경 CI용이 아닙니다.
픽스처는 정확한 SHA 전달, 재시도, 순서가 바뀐 커밋, 자격 보호, 분기, 누락된 이력,
잠금 경합, 경합하는 체크아웃, 상속된 태그 구성, 멈춘 전송 자손 프로세스, 취소, 비밀 정보
출력 억제를 검사합니다. 원격 서비스에 접속하지 않습니다.
