# 인증 정보 만료

연결된 Wizard에서 **인증 정보 만료**를 열어 운영자가 선택한 자동화 프로젝트의 메타데이터를 확인하세요.
이 개요는 읽기 전용이며 인증 정보 교체, 관리자 토큰 생성, CI 변수 변경 또는 외부 서비스에 대한
비밀 값 테스트를 수행하지 않습니다. 비밀 값과 비공개 토큰 조회는 GitLab Rails 내부에 남습니다.
브라우저에는 필터링된 용도, 제공자, 프로젝트, 만료일 및 상태 필드만 전달됩니다.

## 프로젝트 선택 및 모니터링 설정 저장

정확한 namespace/project 경로를 한 줄에 하나씩 입력하세요. 선택한 프로젝트만 확인하며,
설치별로 정해진 프로젝트 이름이나 전체 프로젝트 검색은 사용하지 않습니다.
서로 다른 경로를 최대 8개 지정할 수 있습니다. 사전 알림 기간은 1~90일의 정수로 설정하며 기본값은 14일입니다.

**모니터링 설정을 양식에 저장**은 로컬 양식만 갱신합니다.
일반 **백업**과 **보내기**를 사용한 뒤 다시 연결하고 개요를 새로고침하여 설정을 보존하고 적용하세요.
대화상자를 열거나 날짜를 수정하거나 **메타데이터 새로고침**을 눌러도 설정은 자동으로 전송되지 않습니다.
서버는 저장된 설정을 읽고 결과를 최대 5분간 캐시할 수 있습니다.

런타임 옵션은 정확한 경로의 JSON 배열인 `SYSTEM_CREDENTIAL_PROJECT_PATHS`와
알림 기간인 `SYSTEM_CREDENTIAL_WARNING_DAYS`입니다. 프로젝트 경로 값의 예:

```json
["example/system", "example/wizard"]
```

선택 사항인 `SYSTEM_CREDENTIAL_EXPIRY_METADATA`는 외부 만료일을 기록합니다.
JSON 배열의 각 항목은 `projectPath`, `key`, `expiresAt`만 포함합니다.
각 항목에는 선택된 프로젝트, 지원되는 외부 키 및 실제 달력 날짜를 지정해야 합니다.
외부 날짜 편집기가 이 값을 생성하며 프로젝트와 키의 조합당 하나의 항목만 허용됩니다.
값의 예:

```json
[{"projectPath":"example/system","key":"DOCKERHUB_TOKEN","expiresAt":"2027-01-01"}]
```

## 개요에서 확인할 수 있는 것

서버는 선택한 프로젝트에서 고정된 CI 변수 키 네 개만 읽습니다.
`RENOVATE_TOKEN`, `SYSTEM_RELEASE_GITLAB_TOKEN`, `GITHUB_RELEASE_TOKEN`,
`DOCKERHUB_TOKEN`이며 값은 반환하지 않습니다. 처음 두 키의 경우 GitLab Rails가
새 관리자 토큰을 만들거나 보관하지 않고 기존 로컬 GitLab 개인 접근 토큰의 메타데이터를 조회합니다.
기존 GitLab 메타데이터에서 만료일과 취소 여부를 확인할 수 있습니다.

GitHub와 Docker Hub는 운영자가 만료일을 기록하지 않으면 만료 상태가 **알 수 없음**으로 유지됩니다.
이 날짜에는 **운영자 기록** 표시가 붙습니다. 이는 의도한 외부 인증 정보에 대한 운영자의 기록이며,
제공자의 응답을 검증한 결과가 아닙니다. 토큰이 없거나 인식되지 않거나,
만료일을 얻을 수 없거나 메타데이터에 접근할 수 없는 경우도 **알 수 없음**입니다.
알 수 없음은 유효하거나 만료되지 않는다는 뜻이 아닙니다.

| 상태 | 의미 |
| --- | --- |
| 유효 기간 내 | 확인되거나 기록된 만료일이 사전 알림 기간 이후입니다. |
| 곧 만료됨 | 만료일이 설정된 사전 알림 기간 안에 있습니다. |
| 만료됨 | 만료일에 도달했습니다. |
| 취소됨 | 로컬 GitLab 토큰 메타데이터가 취소를 보고합니다. |
| 만료일 알 수 없음 | 사용할 수 있는 만료일이 없습니다. |

만료일은 해당 날짜를 포함하지 않고 **그 날짜의 UTC 00:00**부터 적용됩니다.
만료일이 오늘인 인증 정보는 이미 만료된 것입니다. 미래 날짜라고 해서 인증 정보가
아직 존재하거나, 인증에 성공하거나, 필요한 범위를 갖추거나, 대상 프로젝트에 접근할 수 있음을 증명하지 않습니다.
별도로 교체한 후에는 기록된 외부 날짜가 오래된 정보가 될 수 있으므로 의도적으로 수정하거나 제거하세요.

## 인증 정보를 소유한 도구로 갱신

해당 용도의 갱신 링크를 열고 저장소에서 관리하는 절차를 따르세요.
Renovate의 기존 `gitlab/renovate/setup.py` 절차는 운영자의 비공개 설정으로
`--apply --rotate --enable`을 지원합니다.
릴리스 메타데이터 접근에는 Reporter 역할, `read_api` 범위 및 명시적인 만료일을 가진
프로젝트 범위의 대체 GitLab 토큰을 만들고, 소유한 System 프로젝트의 보호되고 마스킹된
`SYSTEM_RELEASE_GITLAB_TOKEN` 변수를 교체하세요.
파일 기반 인증 정보가 우선합니다. 해당 비공개 토큰 파일이 설정되어 있다면
운영자의 비밀 저장소를 통해 그 파일을 교체하세요.
GitHub Contents 접근과 선택한 인증 정보 출처는 문서화된
[릴리스 인증 정보 설정](RELEASES.md#trusted-publication-and-retry-behavior)을 따르세요.

GitHub 또는 Docker Hub 게시에는 제공자에서 대체 인증 정보를 만들고,
의도한 릴리스/이미지 저장소로 접근 범위를 제한한 뒤 소유 프로젝트의 해당 보호 CI 인증 정보를 갱신하세요.
마스킹과 보호 참조 범위를 유지하고, 설정된 비공개 파일이 우선하는 경우 그 파일을 사용하세요.
운영자가 기록한 만료일도 동시에 갱신하거나 지우세요.
기존 인증 정보를 취소하기 전에 새 인증 정보로 다음 승인된 게시가 성공하는지 확인하세요.
읽기 전용 만료 개요는 게시 권한이 작동함을 증명할 수 없습니다.
날짜나 메타데이터가 없으면 이 과정 내내 알 수 없음으로 유지됩니다.

인증 정보 값을 브라우저 양식, 공개 설정 내보내기, 저장소 파일, 채팅 및 로그에 넣지 마세요.
만료를 모니터링하기 위해 영구 관리자 토큰을 도입하지 마세요.

일반 설정이나 모니터링 메타데이터를 가져와도 인증 정보가 생성되거나 교체되지 않습니다.
일치하는 Seed가 없는 새 설치에서는 선택한 프로젝트 경로가 원하는 모니터링 대상만 나타냅니다.
자동화가 작동하려면 실제 프로젝트를 다시 만들고 소유한 설정 도구로 필요한 보호 CI 변수를 설정하세요.
메타데이터 가져오기는 비밀 정보 복구가 아닙니다.
