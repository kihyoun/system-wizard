## 3. 애플리케이션과 환경 구성

Wizard의 **프로젝트** 섹션은 이전에 **Proxy**라는 이름이었습니다. 하나의 애플리케이션과
그 **운영 환경**, **Beta**, **Review 앱** 환경을 설명합니다. **프로젝트 추가**로 배포
구성을 만드세요. NGINX 프록시가 구성된 도메인의 요청을 해당 애플리케이션 컨테이너로
전달합니다. 프록시는 애플리케이션 구성의 한 부분입니다.

0장의 일부 이미지에는 이전 **Proxy** 레이블이 남아 있습니다. 현재 인터페이스는 같은 위치에
**프로젝트**를 사용합니다.

새 프로젝트의 **프로젝트 키**는 GitLab 이름 및 경로와 정확히 같습니다. 소문자 a~z와 숫자만
허용하며, 이미 저장된 키의 이름은 변경하지 않습니다.

Wizard를 Sync에 연결하고 먼저 **가져오기**를 사용하세요. **프로젝트 → 프로젝트 추가**에서
네임스페이스를 선택하고 사용 가능 여부를 확인한 뒤, 활성화할 환경과 HTTP/HTTPS 설정을
구성하세요. **저장**은 README와 생성된 CI가 있는 비공개 GitLab 저장소를 만듭니다.
설정 진행 상황은 비동기로 보고합니다. 이미 사용 중인 저장소는 채택하거나 덮어쓰지 않으며,
저장을 반복해도 중복 생성하지 않습니다.

### 3.1 템플릿에서 애플리케이션 시작

생성 대화상자에서 **애플리케이션 템플릿**을 선택하세요.

| 선택 | 생성되는 스타터 |
| --- | --- |
| React + TypeScript + Vite | React 소스, Vite 빌드, 잠금 파일, Dockerfile |
| Angular + TypeScript | Angular 소스, CLI 빌드, 잠금 파일, Dockerfile |
| 일반 웹 프로젝트 | 프레임워크 빌드 없이 HTML, CSS, JavaScript와 Dockerfile |
| 빈 저장소 | 저장소와 CI만 생성합니다. 소스는 나중에 직접 추가합니다 |

처음 세 옵션에는 Dockerfile이 포함됩니다. 저장은 파일과 일치하는 CI를 만들고 라우팅을
구성한 뒤 첫 파이프라인을 시작합니다. 파이프라인은 이미지를 빌드 및 게시하고 HTTP 응답을
확인한 다음 자동 배포를 시작합니다. 수동 배포는 GitLab에서 해당 작업을 직접 시작하세요.

파이프라인 링크를 열고 빌드 및 배포 작업이 성공할 때까지 기다린 다음 애플리케이션 도메인을
확인하세요. 저장소 링크만으로 애플리케이션이 실행 중임을 입증할 수는 없습니다. 이후 생성된
소스에서 직접 작업할 수 있으며 Dockerfile과 파이프라인도 계속 편집할 수 있습니다. 새 저장소의
GETTING_STARTED.md에 로컬 명령이 설명되어 있습니다. 새 Angular와 React 프로젝트는
System Wizard 자체와 마찬가지로 Node 24로 빌드됩니다.

빈 저장소는 아직 실행 중인 애플리케이션이 아닙니다. 이 절차의 파이프라인은 Dockerfile이
포함된 애플리케이션 소스를 기다립니다. 저장소 메타데이터는 가져오기와 JSON 백업/열기에서
유지됩니다. 오류 후 복구를 포함한 전체 안내는 [프로젝트 안내](PROJECT_BOOTSTRAP_GUIDE.md)를
참조하세요.

### 3.2 자동 등록되는 System Wizard

플랫폼에 기본 구성이 있고 GitLab을 사용할 수 있게 되면, 시작 시 Wizard가 활성화된 경우
**wizard**를 첫 프로젝트로 자동 등록합니다. 등록이 끝나면 가져오기를 사용하세요.
운영 환경 URL, HTTP/HTTPS 모드, 인증서 경로는 일반 아래의 실제 Wizard 설정에서
가져옵니다. 로컬에서는 기존 인터페이스가 `http://localhost`에 유지됩니다.

프로젝트는 README와 관리형 CI가 있는 비공개 `root/wizard` 저장소 스캐폴드로 시작합니다.
행을 펼치고 **Wizard 소스 초기화**를 선택해 고정된 애플리케이션 소스를 미리 보고 명시적으로
가져오세요. 준비와 안전한 재시도는 [소스 초기화 안내](WIZARD_SOURCE.md)를 참조하세요.
이 소스 전용 작업은 파이프라인을 시작하거나 다른 인터페이스를 배포하지 않습니다. 초기화 후
**Wizard 빌드 및 검증**은 별도의 읽기 전용 미리 보기를 엽니다. **빌드 파이프라인 활성화**는
관리형 레시피를 명시적으로 설치하고 초기 파이프라인을 시작하거나 복구합니다. 필요한 일치 버전,
검증된 후보 증거, 안전한 복구는 [빌드 절차 안내](WIZARD_BUILD.md)를 참조하세요.
빌드 활성화는 후보를 배포하지 않습니다. 선택적 Review와 Beta 환경에는 명시적인 구성과
수동 GitLab 배포 작업이 필요합니다. 운영 환경 승격은 별도로 보호된 운영자 절차를 사용합니다.
기존 Wizard 컨테이너와 운영 환경 라우트를 재사용하며 중복 프로젝트 프록시는 만들지
않습니다. 인터페이스 설정은 일반에서 관리하세요. 시스템 프로젝트는 프로젝트 목록에서 읽기
전용입니다. 저장소 링크와 구성은 가져오기, 백업, 열기, 보내기, 다시 시작에서 유지됩니다.
반복 시작은 같은 저장소를 재사용합니다.

로컬 `wizard` 키나 관련 없는 GitLab 저장소가 이미 있으면 Bootstrapper는 덮어쓰지 않고
충돌을 보고합니다. 등록 실패는 작동 중인 인터페이스를 대체하거나 중지하지 않습니다.
Bootstrapper 출력을 확인하고 보고된 충돌/준비 상태 문제를 해결한 뒤 다시 시작하여 재시도하세요.

#### Wizard 수동 빌드 및 검사

시작 전에 소스 및 빌드 작업을 제공하는 서로 일치하는 System과 Wizard 버전을 사용하세요.
System 이미지에는 준비된 고정 Wizard 소스 패키지가 들어 있어야 합니다. GitLab, 해당
프로젝트 Registry, `docker` 태그를 받는 공유 Runner를 사용할 수 있어야 합니다. Runner에는
Docker/Buildx 접근 권한과 Registry 연결을 포함하여 관리형 레시피가 사용하는 검토된 Docker
실행기 설정이 필요합니다. 빌드에 충분한 물리 디스크와 RAM이 있는지 확인하고, 자원을 다투는
인프라 빌드를 동시에 실행하지 마세요. 새 가져오기는 고정된 Node 24/React 19/Vite 8 소스와
일치하는 현대적 빌드 레시피를 사용합니다. 기존 레거시 가져오기는 명시적인
[업그레이드 절차](../project-bootstrap/wizard-upgrade/README.md)가 필요합니다. 소스 재가져오기는
업그레이드 수단이 아닙니다.

로컬 WSL 설정에서는 `sudo bash bootstrapper/prepare-local.sh`를 다시 실행하세요.
WSL 다시 시작 후 `registry.localhost`가 더 이상 해석되지 않는 경우에 해당합니다. WSL은 `/etc/hosts`를
다시 생성할 수 있습니다. 준비는 실행 중인 컨테이너를 다시 시작하지 않고 Docker 구성을
다시 불러옵니다. 이후 같은 파이프라인에서 실패한 작업을 재시도하세요.

1. 기존 Wizard 주소를 여세요. **연결** 옆 연필 아이콘으로 구성된 Sync 주소와 현재 Sync
   자격 증명을 입력한 뒤 **제출**을 선택하세요. 최초 설정 후에는 초기
   `http://localhost/sync` 경로가 여전히 맞다고 가정하지 말고 구성된 Sync 도메인을 사용하세요.
2. **동기화 → 가져오기**를 선택하세요. **프로젝트**에서 첫 **wizard** 항목을 펼치세요.
   저장소 링크와 기존 운영 환경 주소를 확인하세요. 관리형 항목이 없으면 먼저 등록을
   해결하세요. **프로젝트 추가**로 두 번째 Wizard 프로젝트를 만들지 마세요.
3. 소스가 이미 초기화되어 있다면 기록을 보존하고 4단계로 넘어가세요. 관리형 빌드 활성화 후
   재가져오기를 하지 마세요. 그렇지 않으면 **Wizard 소스 초기화**를 선택하세요. 미리 보기의
   **저장소**, **소스 리비전**, **파일**을 확인한 뒤 **소스 가져오기**를 선택하고 완료를
   기다리세요. 파이프라인을 시작하지 않고 이 System 버전이 고정한 소스를 가져옵니다.
   소스를 이미 가져왔다면 해당 기록을 유지하세요. 재가져오기는 소스 업그레이드 수단이 아닙니다.
4. 소스 대화상자를 닫고 **Wizard 빌드 및 검증**을 선택하세요. **저장소**, **가져온 커밋**,
   **레시피 버전**을 확인하세요. 미리 보기만으로 파이프라인을 만들거나 저장소를 변경하지 않습니다.
5. **빌드 파이프라인 활성화**를 한 번 선택하세요. 컨트롤러 작업이 끝날 때까지 기다리세요.
   관리형 레시피와 초기 파이프라인을 기록합니다. 브라우저 응답이 중단되면 저장된 작업을
   검사/새로 고침해야 하며, 기록을 삭제하거나 다른 프로젝트를 만들면 안 됩니다.
6. 빌드 대화상자에서 **파이프라인 열기**를 선택하세요. GitLab에서 같은 파이프라인의
   `build:wizard`와 `test:wizard` 작업을 검사하세요. 첫 작업은 고정된 애플리케이션 검사와
   프로덕션 빌드를 실행한 뒤 후보 이미지를 게시합니다. 두 번째는 불변 이미지를 가져와 격리된
   브라우저 후보에서 HTTP, 렌더링된 UI, 프로젝트, SPA 탐색을 검사합니다. Runner가 대기
   중이거나 작업이 실행 중인 상태는 이 검사를 통과한 것이 아닙니다.
7. 작업이 끝나면 Wizard로 돌아와 **상태 새로 고침**을 선택하세요. **후보 검사와 불변
   아티팩트가 검증되었습니다** 및 **검증된 후보 이미지**가 나타날 때까지 기다리세요.
   파이프라인과 `@sha256:…`로 끝나는 이미지 참조를 기록하세요. 녹색 파이프라인만으로
   컨트롤러의 필수 작업 및 일치하는 아티팩트 검증을 대신할 수 없습니다.
8. 증거가 필요하면 GitLab 작업 아티팩트를 검사하세요. `build-evidence.json`은
   `build:wizard`에서, `wizard-evidence.json`과 `browser-evidence/`는
   `test:wizard`에서 확인합니다. 증거는 해당
   파이프라인과 커밋에 속합니다. 현재 레시피는 이 아티팩트를 7일간 보관합니다. 이전 작업이
   녹색이었어도 아티팩트가 만료되면 나중의 검증이 불가능할 수 있습니다.
9. 기존 Wizard가 원래 주소에서 계속 열리는지 확인하세요. 다시 가져오기를 실행하고 같은
   프로젝트/저장소와 운영 환경 주소가 유지되는지 확인하세요. 빌드 검증은 실행 중인
   인터페이스를 대체하지 않습니다. 후보를 배포하려면
   [관리형 Review와 Beta 환경](../project-bootstrap/wizard-environments/README.md)을 구성하고
   수동 GitLab 작업을 사용하세요. 운영 환경 승격과 롤백은 별도의
   [보호된 운영자 절차](../project-bootstrap/wizard-production/README.md)를 사용합니다.

실패 시 [빌드 상태 및 복구 표](WIZARD_BUILD.md#status-and-safe-continuation)를 사용하세요.
같은 GitLab 파이프라인에서 실패한 작업을 재시도한 뒤 상태를 새로 고치세요. **미리 보기 새로
고침**으로 현재 상태를 확인한 뒤, 대화상자에 **활성화 재개**가 제공될 때만 재개하세요.
**파이프라인 생성 결과가 불확실합니다. 새로 고침만 하세요.** 상태에서는 새로 고침만 허용하며
관리자의 검사가 필요합니다. 다른 파이프라인을 강제로 만들려고 영구 체크포인트를 지우지 마세요.
스크린샷, 이슈 댓글, 작업 로그 발췌에 자격 증명을 포함하지 마세요.

### 3.3 공유 Runner와 추가 Runner

Runner 설정에는 서로 다른 두 목적이 있습니다.

| Wizard 위치 | 의미 |
| --- | --- |
| 일반 → GitLab Runner | 여러 GitLab 프로젝트에서 사용할 수 있는 공유 인스턴스 Runner 풀 |
| 프로젝트 → 추가 Runner(선택 사항) | 별도로 제공한 토큰을 사용하는 이 애플리케이션 구성의 추가 Runner 컨테이너 |

추가 프로젝트 Runner는 **0**으로 시작하세요. GitLab 프로젝트에서 인스턴스 Runner를
활성화하고 작업 태그가 일치하면 파이프라인은 공유 풀을 사용할 수 있습니다. 값 0은 공유
Runner를 비활성화하지 않습니다. 이 애플리케이션에 추가 컨테이너를 시작하지 않을 뿐입니다.

추가 Runner를 어떤 프로젝트에서 사용할 수 있는지는 GitLab 등록과 토큰이 결정합니다.
Runner를 프로젝트 키에 연결하는 것만으로 해당 GitLab 프로젝트로 제한되지는 않습니다.
2장의 자동 토큰 생성은 공유 인스턴스 풀에 적용됩니다.
