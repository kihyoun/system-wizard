# 일회용 플랫폼 인수 검사

`candidate.js`는 비공개 데몬에서 명시적인 스모크 또는 전체 플랫폼 시나리오를 실행합니다.
격리된 매니페스트와는 별개이며, 오프라인 전송 계층은 Docker를 시작하지 않고 수명 주기 계약을 검증합니다.
필수 루트 CI 플랫폼 검증은 설정 및 Seed 복구, 캐시하지 않은 비공개 Wizard 이미지 가져오기,
로컬 ACME 갱신을 포함한 전체 시나리오를 실행합니다.

## 경계 및 준비 사항

Node 24와 대상 외부 Docker 데몬에 대한 Docker CLI 접근을 갖춘 신뢰할 수 있는 Linux 실행 호스트를 사용하세요.
기존 System 설치, WSL 계정, 로컬 Seed, 비공개 설정, 전역 이름의 플랫폼 컨테이너 또는
워크스테이션 경로는 입력값이 아닙니다.
실행기는 CI 컨테이너 내부에서도 실행할 수 있습니다.
HTTP 요청은 CI 컨테이너의 루프백이 아니라 비공개 후보 Bootstrapper 내부의 Node에서 실행합니다.
외부 데몬에는 포트를 공개하지 않습니다.
HTTP 검사는 소유한 후보 내부 Node에서 비공개 브리지 게이트웨이와 비공개 NGINX를 통해 실행합니다.

실행기는 무작위 이름과 소유권 라벨이 있는 **특권 DinD** 컨테이너 하나,
내부 네트워크 및 Docker 데이터 볼륨을 만듭니다.
DinD는 자체 Unix 소켓을 가지며 호스트 소켓은 마운트하지 않습니다.
고정 `system_*` 이름, 내부 Docker 네트워크, 포트 80/8071/5050 및 서비스 볼륨은 해당 데몬 안에 한정됩니다.
내부 Bootstrapper는 정상 System 시작에 필요하므로 이 **내부** 소켓을 받습니다.
신뢰할 수 없는 후보 코드에 이 하네스를 재사용하지 마세요.
특권 Docker 실행은 호스트 커널을 공유하므로 호스트 격리를 보장하지 않습니다.
외부 플랫폼에는 추가 GitLab Runner를 준비하지 않습니다.

실제 실행 전에 정확한 후보 및 DinD 이미지를 검토하고 조정자의 자원 임대를 받아 테스트 시간을 합의하세요.
DinD 컨테이너는 CPU 4개와 RAM 12 GiB로 제한됩니다.
외부 호스트, 이미지 아카이브, 이미지 추출 및 GitLab 데이터 볼륨을 위한 추가 여유를 확보하세요.
Docker 볼륨은 디스크 할당량을 강제하지 않습니다.
호출 전에 실행기 외부에서 디스크/RAM 검사와 임대를 완료해야 합니다.
내부 외부 네트워크는 외부 의존성 다운로드를 막으므로 서비스 이미지를 미리 로드해야 합니다.
전체 Runner/레지스트리 시나리오에는 명시된 도우미와 빌드 이미지 입력값도 필요합니다.

## 명시적 입력값

정확한 Docker DinD 릴리스와 **검증된 sha256 다이제스트**를 `daemonImage`로 지정한 공개 JSON 명세를 만드세요.
유동적이거나 임의로 만든 기본값은 의도적으로 없습니다.
`images`에는 정확히 다음 역할이 있어야 합니다.

| 역할 | 입력 | 비공개 데몬 태그 |
| --- | --- | --- |
| `candidate` | 고정된 Wizard 파일과 설치된 Sync 의존성을 포함한 전체 후보 System 이미지 | `system-candidate:under-test` |
| `wizard` | 준비된 Wizard 웹 이미지 | `systembootstrapper/wizard` |
| `gitlab` | 선택한 지원 GitLab 이미지 | `candidate-gitlab:under-test` |
| `runner` | 호환되는 GitLab Runner 이미지 | `candidate-runner:under-test` |
| `nginx` | 선택한 NGINX 이미지 | `nginx:latest` (내부 호환 별칭 전용) |

각 역할의 `archive`는 실행 호스트의 절대 경로 일반 이미지 아카이브 파일이며
`docker image save`로 생성합니다. `id`는 정확한 `sha256:` 이미지 ID이며
`docker image inspect --format '{{.Id}}' IMAGE`에서 얻습니다.
이는 레지스트리 매니페스트 다이제스트가 아니라 **이미지 ID**입니다.
데몬은 레지스트리 다이제스트로 고정하며, 로드한 각 역할은 예상 로컬 별칭을 할당하기 전에 이미지 ID로 검증합니다.
아카이브에는 필요한 서비스 이미지 레이어가 모두 있어야 합니다.
실행기는 명시한 파일만 스트리밍하며 체크아웃, 호스트 Docker 저장소 또는 기존 데이터는 전송하지 않습니다.
Bootstrap은 소유한 비공개 호스트 루트로 커밋된 `prepare-local` 저장소 보호를 호출하고,
해당 데몬 루트 파일시스템의 `/candidate-data/platform`에 운영 디렉터리를 만들며
설정을 `/state`에 마운트합니다.
별도로 저널링되는 경량 소유자가 `/seed-device`에 외부 백업 볼륨을 제공하며,
설정된 백업 마운트 `/external-seed`는 정상 시작 중 존재하지 않습니다.
이는 일회용 후보 경로이며 운영 환경에 연결된 볼륨이 아닙니다.
모든 Docker 작업에는 자체 제한 시간과 남은 전체 예산이 함께 적용됩니다.
비공개 설정이나 인증 정보 없이 빌드한 후보 이미지를 사용하세요.

역할 하나의 형태 예:

```json
{"archive":"/job/images/candidate.tar","id":"sha256:<64 verified hexadecimal characters>"}
```

`readinessMilliseconds`는 선택 사항이며 1,000~1,200,000 범위입니다.
스모크 준비 검증별 기본값은 1,200,000입니다.
일반 수명 주기 예산은 20분이며 전체 ACME 복구는 모든 소유자가 25분 예산 하나를 공유합니다.
두 제한은 범위가 제한된 Docker/HTTP 작업 사이에서 확인합니다.
각 스트리밍 아카이브 로드는 최대 10분, 다른 Docker 작업은 2분,
개별 HTTP 요청은 10초로 제한됩니다.
모든 Docker 작업 전에 이벤트 루프를 명시적으로 양보하여 대기 중인 신호 콜백을 전달합니다.
취소는 작업 사이에 확인하므로 아카이브 로드가 협력적 취소를 최대 10분 지연할 수 있습니다.
CI는 이 경계 이후의 정리를 허용하고 강제 종료에 대비한 실행 기록을 보존해야 합니다.

커밋된 LF 체크아웃에서 실행하세요. 서명된 예시는 변경 없이 검증되어야 합니다.

```sh
SYSTEM_DISPOSABLE_CANDIDATE=I_ACCEPT_PRIVILEGED_DISPOSABLE_EXECUTION \
  node tests/e2e/candidate.js /job/candidate-spec.json
```

임시 무작위 GitLab root 및 Sync 인증 정보는 메모리에서 생성하며,
stdin을 통해 일회용 데몬/후보에만 기록합니다.
명령 인수, 공개 명세 및 보고서에는 포함하지 않습니다.
설정은 공개 예시에서 서명 뒤의 명명된 할당만 바꾸어 생성합니다.
Cube가 유효하지 않으면 안전하게 중단합니다. 비공개 호스트 설정은 읽지 않습니다.

## 증거 및 정리

초기 스모크 검증에는 라우팅된 Wizard HTML 응답, 실제 Sync 로그인 및
동일한 임시 Sync 인증 정보로 서명된 주 설정을 인증하여 가져오기가 필요합니다.
이는 브라우저 렌더링이나 GitLab/Runner/레지스트리 준비를 입증하지 않습니다.
Wizard 소스/빌드 절차를 활성화하거나 배포 파이프라인을 만들거나 운영 배포를 수행하지 않습니다.
정상 Bootstrap의 기본 Wizard 등록은 일회용 후보 내부에서만 발생합니다.

`test-results/e2e/<run-id>/results.json`은 범위가 제한된 단계 결과,
정확한 소유 자원 식별 정보 및 이미지 ID를 기록하고 `junit.xml`은 CI 테스트 증거를 제공합니다.
원본 Docker 로그, HTTP 본문, 토큰, 인증 정보 또는 하위 프로세스 오류 출력은 공개하지 않습니다.
진단에는 정제된 단계/실패 코드를 사용하세요.
외부 자원을 만들기 전에 실행 기록을 체크포인트로 저장하여 중단된 생성을 조정할 수 있습니다.
각 기록은 같은 디렉터리의 고유 임시 파일에 완전히 기록하고 fsync한 뒤 닫아,
이전 기록을 원자적으로 이름 변경하여 교체합니다.
쓰기 중단이나 디스크 부족 시 이전의 완전한 기록을 유지하며,
생성 후 전체 ID 체크포인트가 실패했으면 대기 중인 생성 이름도 보존됩니다.
갑작스러운 프로세스 종료는 작은 불완전 `.tmp` 파일을 남길 수 있지만 정리는 `results.json`만 읽습니다.
Linux 실행 호스트에서는 각 이름 변경 후 해당 디렉터리도 fsync합니다.
이전 실패 체크포인트가 영구 반영 없이 만든 기존 경로까지 포함해,
보고 디렉터리와 조상 디렉터리를 자원 생성 전에 말단부터 파일시스템 루트까지 동기화합니다.
동기화 실패는 체크포인트를 중단합니다.
이 보장은 파일시스템과 저장소가 fsync를 준수해야 성립하므로 실행 기록을 영구 저장소에 보관하세요.
네이티브 Windows 픽스처는 프로세스 충돌 시 원자적 교체를 검증하지만,
Node의 Windows 파일시스템 API는 같은 디렉터리 fsync 보장을 제공하지 않습니다.
Windows 픽스처 성공을 전원 손실 내구성의 증거로 제시하면 안 됩니다.

정리는 성공, 실패 및 협력적 SIGINT/SIGTERM 시 실행됩니다.
중지된 컨테이너도 나열하고 자원 부재와 데몬 접근 불가를 구분하며,
삭제 전에 정확한 이름, 소유권 라벨 및 전체 ID를 확인합니다.
실패하거나 다른 소유자의 컨테이너는 의존하는 볼륨/네트워크 해체를 차단합니다.
정리 실패는 성공을 실패로 바꾸지만 원래 실패를 성공으로 바꾸지는 않습니다.
전역 정리를 사용하지 않으며 다른 실행의 자원을 건드리지 않습니다.

SIGKILL, 전원 손실 또는 데몬 접근 불가 후에는 기록을 보관하고,
대상 외부 데몬을 다시 사용할 수 있을 때 다음 정리 진입점만 재시도하세요.

```sh
SYSTEM_DISPOSABLE_CANDIDATE=I_ACCEPT_PRIVILEGED_DISPOSABLE_EXECUTION \
  node tests/e2e/candidate.js cleanup test-results/e2e/RUN_ID/results.json
```

ID 없는 대기 중 생성은 저널에 남긴 고유 이름으로 검사합니다.
삭제 전에 소유권과 결과 전체 ID를 증명해야 하며 알 수 없거나 다른 소유자의 인스턴스는 거부합니다.
정리는 기존 System 설치를 연결하거나 복사하거나 파괴하지 않습니다.
프로세스 강제 종료 시 즉각적인 정리는 보장할 수 없으므로,
CI는 실행 기록을 보존하고 독립적인 정리 훅을 실행해야 합니다.

## 오프라인 수명 주기 계약

네이티브 Node 오프라인 픽스처는 명령 구성, 비공개 데몬 소켓 경계, 루프백 바인딩,
정확한 이미지 식별 정보, 성공 및 거부된 가져오기, 서명 보존,
임시 인증 정보/보고서 분리, 시간 초과와 취소, 중지/부재 자원,
대기 생성 복구, 타 소유 자원 거부 및 데몬/삭제 실패를 다룹니다.
회귀 검사는 부분 실행 기록 쓰기 중 자식 프로세스를 종료하고,
생성 후 ID 체크포인트를 실패시키며 이전 대기 기록을 복구하고,
복사와 로드 사이에 매크로태스크 SIGTERM 처리기를 전달합니다.
순서가 지정된 주입 IO 픽스처는 Linux 디렉터리 영구 반영과
조상 또는 이름 변경 후 동기화 실패 이후 자원 생성 거부도 확인합니다.
Docker나 실제 HTTP를 호출하지 않습니다.

```sh
node tests/shared/disposable-candidate-contract.js
```

이 오프라인 픽스처는 특권 후보 실행이나 실제 GitLab 파이프라인을 입증하지 않습니다.
해당 동작은 필수 전체 플랫폼 검증을 실행하세요.
기존 `*/live/` 스크립트는 자동 가져오기하지 않으며,
고정 이름 가정을 소유한 비공개 데몬에 맞게 명시적으로 조정해야 합니다.

## 필수 전체 플랫폼 CI

`test:platform-candidate`는 모든 격리/이미지 테스트 후 실행되고 기존 게시 단계를 차단합니다.
신뢰할 수 있는 Node 24 / Alpine 부모는 System과 동일하게 고정된 CLI 도구를 설치하며,
전체 System 컨텍스트와 검증된 고정 스냅샷의 Wizard를 빌드하고 고정 서비스 이미지를 미리 로드합니다.
작업은 GitLab 리소스 그룹으로 직렬화됩니다.
이미지 준비에는 별도의 제한 예산이 있고 비공개 실행의 일반 제한은 20분이며,
ACME 복구에서는 하나의 공유 25분 제한으로 늘어납니다.
Runner 호스트에는 후보 RAM 12 GiB와 기존 플랫폼/작업 여유,
이미지 아카이브, 추출 및 GitLab 상태를 저장할 충분한 디스크가 필요합니다.

CI 명세는 `fullAcceptance: true`를 명시하고
`supportImages.helper`로 일치하는 고정 Runner 도우미 이미지를 제공합니다.
라우팅된 HTML과 인증된 서명 설정 가져오기 외에도,
전체 실행기는 새 GitLab과 Runner를 검증하고 중복 풀이나 활성 설정 인증 정보 없이 등록을 반복하며,
소유한 비공개 프로젝트를 만들고 아티팩트 전달을 포함한 실제 Docker 빌드/푸시/다운로드/실행 파이프라인을 실행합니다.
의도적으로 실패시킨 작업이 후속 배포 작업을 차단하는지도 확인합니다.
임시 API 인증 정보를 취소하고 HTTP 401을 확인한 뒤 Seed 주기를 위해 서비스를 중지합니다.
아래 설정 및 Seed 복구 어댑터는 같은 실행에서 외부 백업에서 새 로컬 환경으로 이어지는
수명 주기와 실패 보호를 실행합니다. 운영 환경 배포는 수행하지 않습니다.

매니페스트는 개별 단계 결과와 정제된 숫자 파이프라인/작업/프로젝트 식별 정보를 기록합니다.
실패한 파이프라인은 정제된 작업 상태/이유를 남기며 원본 추적 로그,
인증 정보, 설정 또는 Docker 출력은 보존하지 않습니다.
셸 트랩과 GitLab `after_script`가 모두 소유권을 확인한 정리 기록을 재실행합니다.
작업 라벨이 있는 빌드 이미지 태그만 제거하고 공유된 고정 공개 이미지 캐시는 유지합니다.
전역 정리는 사용하지 않습니다. 강제 호스트 손실 후에도 데몬에 접근할 수 있게 되면 보존된 기록을 재실행해야 합니다.

## 설정 및 Seed 콜드 복구

이미지 준비는 커밋된 소스에 Seed 매니페스트 구현이 있으면 `recovery.js`를 요구하고,
`recoveryAcceptance`를 활성화하며 새로 빌드한 Wizard 이미지에서 실제 Wizard 설정 내보내기 모델 번들을 추출합니다.
내보내기 도구는 SHA-256과 고정 Wizard 소스 리비전으로 확인하는 명시적 비공개 파일 입력값입니다.
ZIP은 백업과 같은 모델 및 생성기를 사용하며 설정만 포함합니다.

어댑터는 합성 GitLab 사용자, 저장소 HEAD, 이슈,
암호화된 CI 변수 및 기존 레지스트리 다이제스트를 기록합니다.
토론과 답글이 있는 별도 소스 브랜치 및 초안 MR도 만듭니다.
기본 브랜치는 변경하지 않으며 작은 픽스처 커밋은 CI를 건너뜁니다.
로컬 ACME가 없으면 합성 TLS 인증서와 계정/갱신 구성을 만들고,
해당 단계가 있으면 실제 픽스처 발급 인증서를 사용합니다.
인증된 API로 저장된 주/프로젝트 설정을 가져와 Wizard 모델로 내보내고
실제 제어된 콜드 Harvest를 실행합니다.
해당 ZIP과 완료 표식이 있는 Seed만 원래 소유 DinD 데몬 밖으로 나갑니다.
바이너리 전송은 파일 디스크립터를, 체크섬은 크기가 제한된 버퍼를 사용합니다.
비공개 아카이브는 권한 0700 임시 디렉터리 아래에 0600으로 저장하며 공개 CI 아티팩트나 보고서에 넣지 않습니다.

새 소유 데몬을 시작하기 전에 원래 데몬, Docker 데이터 볼륨 및 소유 백업 볼륨을 제거합니다.
복구는 다른 빈 데이터 루트를 사용하고, 커밋된 소스와 고정 공개 의존성에서 빌드한 명시적 이미지만 다시 로드합니다.
커밋된 호스트 루트 보호로 새 로컬 운영 저장소를 준비하고,
프로비저닝 전에 실제 ZIP을 가져오며 완료된 Seed만 별도 소유 백업 마운트에 추출합니다.
백업 저장소가 없을 때는 실행 중인 서비스를 그대로 유지해야 합니다.
전역 운영 임대는 백업 대상과 독립적으로 작업을 배제하며,
복원은 데이터를 쓰기 전에 비어 있지 않은 대상과 손상된 페이로드를 거부합니다.
임시 도우미로 실제 Seed를 적용하고 새 소스의 갱신 경로 재작성기를 실행한 뒤,
서비스 시작 전에 두 백업 마운트를 모두 분리합니다.
그런 다음 인증된 실제 ZIP 보내기가 백업 저장소 없이 실제 컨트롤러 다시 시작을 유발하고,
이후 가져오기 및 서비스 검사를 수행합니다.
이전 운영 설정 디렉터리, Runner 작업 공간 또는 명시되지 않은 이미지 아카이브를 마운트하거나 읽지 않습니다.
예상 인증 정보와 식별 정보는 검증 기준으로만 유지하며 복구 입력값으로 기록하지 않습니다.

복원된 인스턴스는 예상 호스트/SNI로 CA 검증 HTTPS,
인증된 설정 가져오기, 계정/인증서/갱신 경로 보존 및
GitLab 사용자/프로젝트/저장소/이슈/암호화 설정/레지스트리 식별 검사를 통과해야 합니다.
픽스처는 명시적 `WIZARD_ALIASES` 설정을 내보냅니다.
해당 별칭은 HTTP와 CA 검증 HTTPS에서 설정된 기준 Wizard로 `308` 리디렉션을 반환해야 하며,
인코딩된 경로, 반복 쿼리 키 및 인코딩된 쿼리 값을 정확히 유지해야 합니다.
두 프로토콜은 소유한 HTTP-01 챌린지를 직접 제공해야 하며,
없는 챌린지에는 `404`와 `Location` 없는 응답을 반환해야 합니다.
이 검사는 백업 전, 재렌더링/다시 불러오기 및 진입 프록시 다시 시작 후,
복원 호스트에서 다시, 복원 설정 보내기가 컨트롤러를 다시 시작한 후에도 실행됩니다.
합성 인증서에는 별칭 SAN을 포함하므로 리디렉션만으로 호스트 이름 검증 실패를 숨길 수 없습니다.
MR 복구는 정확한 소스 브랜치 커밋, MR 식별 정보, 제목, 설명, 상태, 작성자 및 생성 시각,
그리고 토론 메모 두 개의 ID, 내용, 작성자, 시각 및 해결 플래그를 확인합니다.
보고서는 불리언 `mergeRequestRecoveryVerified`만 공개하며 비공개 픽스처 내용은 공개 아티팩트가 아닙니다.
복원 실행 기록은 범위가 제한된 `evidence.storage` 불리언 여섯 개를 게시합니다.
`localLiveVerified`, `externalSeedRestored`, `backupDetached`,
`missingBackupGuardVerified`, `globalLeaseVerified`,
`invalidRestoreGuardVerified`입니다.
필수 복원 단계는 `storage-global-live-lease`,
`storage-refuse-nonempty-and-corrupt-restore`,
`storage-detached-backup-normal-operation`입니다.
이는 실제 네이티브 검증이며 선택된 저장소 설정에서 추론한 주장이 아닙니다.

실제 Runner/레지스트리 CI와 실패 검증을 반복한 뒤,
Harvest 전에 기록한 원래 레지스트리 블롭을 다운로드하고 실행하는 추가 실제 CI 작업을 수행합니다.
두 수명 주기는 원래 전체 마감 시간과 취소 플래그를 공유합니다.
각각 독립적인 소유권/체크포인트 기록과 정리를 가지며,
정리 실패는 인수 검사를 실패시키고 대상 복구를 위해 비공개 입력값을 보존합니다.

합성 TLS만 사용하는 실행은 의도적으로 `acmeRenewalVerified: false`를 보고합니다.
복원된 갱신 파일은 Certbot/ACME 갱신의 증거가 아닙니다.
실제 갱신/배포를 입증하려면 아래 로컬 ACME 시나리오도 통과해야 합니다.
오프라인 어댑터 테스트에는 신뢰 CA를 사용하는 실제 임시 HTTPS,
잘못된 호스트 및 다른 CA 거부, 수명 주기 순서, 취소,
스트림 경계 및 정리 실패 처리가 포함됩니다.
이는 콜드 실행을 통과했음을 입증하지 않습니다.

기본 콜드 픽스처는 명시적으로 소스에서 빌드한 로컬 Wizard 이미지를 사용합니다.
기록 시 기존 `WIZARD_IMAGE`, GitLab/Runner 버전 및 호스트 바인딩 할당을
픽스처 기본값으로 바꾸지 않고 보존합니다.
명시적 `privateWizardRecovery` 시나리오가 없으면 복원된 비공개 Wizard 레지스트리 고정은
`wizard-pin-recovery-artifact-not-declared`로 실패하며 로컬 픽스처 이미지로 조용히 바꾸지 않습니다.

비공개 이미지 시나리오는 관리형 Wizard 프로젝트의 별도 브랜치에서 실제 CI 작업으로
명시된 소스 빌드 Wizard 이미지의 파생 이미지를 게시합니다.
고유 표식 레이어 덕분에 이미지 ID는 준비된 모든 아카이브와 다릅니다.
실제 내보낸 설정은 CI가 게시한 레지스트리 다이제스트를 고정합니다.
새 데몬에는 시작 전에 해당 다이제스트 참조와 비공개 이미지 ID가 모두 없어야 합니다.
Seed 복원 후 새 소스의 시작 도우미가 임시 프로젝트 범위 `read_registry` 배포 토큰으로 정확한 이미지를 가져옵니다.
어댑터는 실행 중인 Wizard의 이미지 ID와 표식을 검증하고 활성 예약 복구 토큰이 남아 있지 않은지도 확인합니다.
그 후에만 보고서가 `privateWizardPinVerified: true`를 표시할 수 있습니다.
픽스처는 이전 Docker 로그인, 비공개 이미지 아카이브 또는 대체 이미지를 제공하지 않습니다.
이 시나리오에는 실제 후보 실행의 성공이 필요하며 구성 요소 계약은 통합 증거가 아닙니다.
새 호스트는 이전 Docker 로그인에 의존해서는 안 되고,
로컬 이미지 복구 성공만으로는 비공개 고정의 경우를 검증할 수 없습니다.

## 로컬 ACME 발급 및 갱신

`local-acme.js`는 전체 어댑터, 신뢰 파일 및 호스트 스크립트가 있을 때
이미지 준비가 활성화하는 `acmeRenewalAcceptance` 단계를 구현합니다.
계약이 일부만 있으면 플랫폼 생성 전에 실패합니다.
`prepare-acme-images.js`는 해당 모듈에 지정된 정확한 공개 이미지 고정 세 개만 준비하며,
반환값이 필수 `spec.acmeImages`입니다.
고정 Certbot 아카이브에는 명시적 이미지 ID와 SHA-256이 있습니다.
커밋된 공개 Pebble TLS 신뢰 인증서의 출처/해시는 `acme-fixture/README.md`에 별도로 문서화하며,
일반 신뢰 저장소에 설치하지 않습니다.

인증 기관과 DNS 서버는 공개 포트가 없는 독립 소유 내부 Docker 브리지에서
각각 192 MiB와 64 MiB를 사용합니다. 원래 플랫폼 데몬을 삭제해도 유지됩니다.
각각 기존 소유권 저널과 보호된 정리를 사용하며 소유자당 컨테이너/네트워크/볼륨은 최대 하나입니다.
짧은 초기화기는 네트워크 없이 실행하며 이미지가 선언한 볼륨을 tmpfs로 재정의합니다.
모든 소유자는 원래 후보의 절대 마감 시간과 취소를 상속합니다.
확장된 `acmeRenewalAcceptance: true` 시나리오는 플랫폼 호스트 두 개와 픽스처 소유자를 포함하여
수명 주기 예산 1,500초 하나를 공유합니다.
일반 후보는 1,200초 예산을 유지하며 개별 단계가 예산을 초기화하지 않습니다.
외부 스크립트와 CI 작업 제한에도 수명 주기 예산 외에 준비, 게시 및 독립적인 정리 여유를 남겨야 합니다.
강제 종료 정리는 이 픽스처 소유자보다 무거운 플랫폼 소유자를 먼저 제거해야 합니다.

DNS 픽스처는 테스트 도메인을 각 소유 데몬의 비공개 브리지 주소로 지정합니다.
Pebble은 NGINX 포트 80에 실제 HTTP-01 요청을 보내 검증합니다.
인증 재사용은 비활성화되며 검증은 절대 우회하지 않습니다.
설정 백업과 콜드 Harvest 전에 실제 인증서/계정을 만듭니다.
호스트 전환 후 동일한 계정 키와 인증서를 검증하고,
잘못된 DNS 대상에서는 갱신이 실패해야 하며 올바른 새 대상에서는 실제 갱신이 성공하여
인증서 일련번호가 바뀌어야 합니다.
최초 발급에는 Wizard, Sync 및 설정된 별칭 이름을 포함하므로 Pebble이 별칭 HTTP-01 경로도 검증합니다.
갱신 후 Wizard와 별칭은 모두 새 일련번호를 제공해야 합니다.
갱신 인수를 기록하기 전에 별칭은 정확한 HTTP/HTTPS 리디렉션 및 직접 챌린지 검사도 계속 통과해야 합니다.
검증된 HTTPS는 인증된 픽스처 제어 채널에서 가져온 독립적으로 생성된 발급 루트를 사용합니다.

실제 새 소스의 갱신 임대 및 인증서 설치/다시 불러오기 스크립트는
실제 바인드 마운트와 마운트 유틸리티가 있는 셸 전용 GitLab 이미지 호스트 하네스에서 실행됩니다.
유일한 클라이언트 어댑터가 Docker로 Certbot을 전달하며,
실제 Certbot 배포 이벤트가 변경되지 않은 소스 설치 훅을 실행합니다.
Docker CLI와 musl 로더는 명시된 새 컨트롤러 이미지에서 가져옵니다.
이전 호스트 실행 파일, 패키지 설치, 운영 경로 또는 운영 소켓은 사용하지 않습니다.
이는 systemd 타이머 예약이나 공개 Let's Encrypt를 에뮬레이션하지 않습니다.

오프라인 계약은 입력/신뢰, 작은 자원 한도, 소유권, 정리,
부정 검증 조건 및 실제 HTTPS 신뢰/SNI를 검증하며 ACME 복구 통과를 입증하지 않습니다.
`acmeRenewalVerified`는 실제 복원 계정, 갱신, 배포 및 CA 검증 HTTPS 단계가
모두 통과한 후에만 true가 될 수 있습니다.
정리는 작은 클라이언트와 공유 픽스처 자원을 소유한 인증 기관보다 무거운 플랫폼 소유자를 먼저 제거합니다.

설정 비교는 리터럴 셸 할당을 실행하지 않고 해석합니다.
따옴표가 있거나 없는 export를 정확한 값으로 비교합니다.
부분 문자열, 중복 할당, 셸 확장 및 셸 명령으로 검사를 통과할 수 없습니다.
명시적인 소스 소유 실패 코드만 정리 재시도 이후에도 유지됩니다.

## GitLab 후속 버전 마이그레이션 인수 검사

커밋된 보안 릴리스 프로필은 명시적 아카이브 입력값에 `supportImages.previousGitlab`,
`supportImages.previousRunner` 및 `supportImages.previousHelper`를 추가합니다.
`images.gitlab`, `images.runner`, `supportImages.helper`는 패치된 후속 버전을 식별합니다.
격리된 기준 및 콜드 복구 단계는 의도적으로 이전의 고정 GitLab, Runner 및 도우미 이미지를 시작합니다.
독립적인 `:target` 별칭은 새 이미지를 기준 이미지 대신 사용하지 않고 유지합니다.
모든 아카이브는 변경 불가능한 공개 참조로 다운로드하고,
내부 데몬을 만들기 전에 검사하여 로드합니다.
운영 데이터, 네트워크, 소켓 또는 인증 정보는 후보 플랫폼의 입력값이 아닙니다.

기존 Runner, 레지스트리, 콜드 복구 및 ACME 시나리오가 통과하면
`gitlab-upgrade.js`가 업그레이드 전 합성 사용자/프로젝트/이슈,
병합 요청/토론 및 암호화 변수 식별 정보를 추가로 만듭니다.
비공개 데몬 안에서 아카이브로 검증한 별칭만 사용하여 운영 환경과 같은 저장소 업그레이드 엔진을 호출합니다.
운영 CLI는 이 별칭을 허용하지 않습니다.
정상 중지된 이전 데이터베이스를 체크포인트로 저장하고 실제 상태를 패치 버전으로 마이그레이션한 뒤 식별 정보를 검증합니다.
새 Runner 작업은 업그레이드 전에 게시된 이미지 블롭을 다운로드하여 실행합니다.
마지막으로 정확한 콜드 체크포인트와 이전 이미지를 복원하고 식별 검사를 반복합니다.

복원된 후보의 실행 기록에는 필수 단계 세 개인
`gitlab-upgrade-migrated-data`, `gitlab-upgrade-registry-ci`,
`gitlab-upgrade-restored-checkpoint`와 범위가 제한된 `evidence.gitlabUpgrade`
이미지 식별 정보 및 완료 플래그가 포함됩니다. 최종 정리도 통과해야 합니다.
외부 실행 기록은 범위가 제한된 마이그레이션 증거를 복사하며,
상세 마이그레이션 단계는 복원된 후보 기록에 속합니다.
원본 비공개 체크포인트, 설정, 인증 정보 및 데이터베이스 로그는 공개 CI 아티팩트에 넣지 않습니다.

선택적인 후속 버전 시나리오는 앞선 콜드 복구 시나리오와 두 버전 전환을 포함하여
유한한 전체 후보 예산 60분을 공유합니다.
네이티브 업그레이드와 롤백 준비는 각각 900초를 허용하며,
1,200초 호출 제한과 같은 절대 후보 마감 시간 안에서 실행합니다.
준비 완료에는 여전히 백그라운드 마이그레이션 완료가 필요하며 마이그레이션 배치 성공만으로는 충족되지 않습니다.
이 시나리오는 기존 직렬화 리소스 그룹과 비공개 데몬 12 GiB 상한을 사용합니다.
시작 전에 실제 호스트 여유를 확인하세요.
플랫폼 작업은 70분 작업 제한 안에서 65분 스크립트와 별도 2분 정리를 허용하여
준비, 게시 및 아티팩트 수집 시간을 남깁니다.
일반 스모크 및 ACME 전용 수명 주기 예산은 변경되지 않습니다.
모의 어댑터 계약 통과는 실제 마이그레이션 성공이 아니므로 전체 플랫폼 CI 검증을 증거로 사용하세요.

## 배포 후 안내형 미리보기 인수 검사

[네이티브 안내형 미리보기 인수 도구](GUIDED_PREVIEW_ACCEPTANCE.md)는
승인된 컨트롤러를 의도적으로 배포한 후 새 소스 가져오기,
실제 필수 Wizard 푸시/MR 파이프라인, 소스 기준 연결 및 Review 배포/중지를 검사합니다.
명시적인 비공개 운영자 입력과 네이티브 로컬 Docker 소켓을 사용합니다.
일회용 명세나 추가 CI 파이프라인으로 활성화되지 않습니다.
검사 전용 계획이나 오프라인 픽스처 통과만으로 실제 운영자 인수 검사를 실행했다고 입증할 수 없습니다.
