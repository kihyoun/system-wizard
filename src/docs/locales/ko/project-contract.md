# 프로젝트 부트스트랩

프로젝트 부트스트랩은 애플리케이션 구성을 비공개 GitLab 저장소, 관리형 CI, 환경 네트워크
및 NGINX 라우팅에 연결합니다. Wizard의 **프로젝트 → 프로젝트 추가 → 저장** 흐름은 인증된
Sync 서비스를 통해 프로비저닝을 수행합니다. 브라우저 절차는
[운영 가이드](PROJECT_BOOTSTRAP_GUIDE.md)를 확인하세요.

## 애플리케이션 템플릿

| 템플릿 | 생성되는 애플리케이션 |
| --- | --- |
| React | TypeScript/Vite 애플리케이션, 잠긴 의존성, Node 24 빌드 및 NGINX 런타임. |
| Angular | TypeScript/Angular CLI 애플리케이션, 잠긴 의존성, Node 24 빌드 및 NGINX 런타임. |
| 일반 웹 프로젝트 | Node 빌드 없이 NGINX가 제공하는 프레임워크 없는 HTML, CSS 및 JavaScript. |
| 빈 저장소 | README와 관리형 CI. 애플리케이션 소스와 루트 Dockerfile은 별도로 제공해야 합니다. |

템플릿 파일은 `project-bootstrap/templates/` 아래에서 버전 관리됩니다. 생성 후에도 소스,
Dockerfile, 런타임 구성 및 CI를 편집할 수 있습니다. 생성된 애플리케이션 파이프라인은
이미지를 빌드하여 인스턴스 레지스트리에 게시하고, HTTP 스모크 검사를 수행하며,
구성된 자동/수동 설정에 따라 활성 환경을 배포합니다. 파이프라인은 특정 브랜치 이름을
가정하지 않고 `CI_DEFAULT_BRANCH`를 사용합니다.

## 저장소 식별 정보와 충돌

저장소 표시 이름과 경로는 프로젝트 키와 정확히 일치합니다. 키 `mywebapp`은
`<selected-namespace>/mywebapp`을 만듭니다. 새 키는 `^[a-z0-9]+$`와 일치해야 합니다.
UI와 백엔드는 공백, 문장 부호, 대문자 및 빈 키를 거부하며 입력을 조용히 정규화하지
않습니다. 기존에 저장된 키는 계속 가져올 수 있습니다. GitLab 예약 이름 또는
네임스페이스 권한 오류는 별도로 보고됩니다.

운영 환경, Beta 및 Review 도메인은 독립적인 설정입니다. 도메인을 바꿔도 저장소 이름은
바뀌지 않습니다. 사용 중인 대상은 생성을 차단합니다. Bootstrapper는 이를 덮어쓰거나
조용히 연결하거나 접미사가 붙은 이름을 만들지 않습니다. 저장된 작업은 동일 요청의
성공적인 재시도를 식별합니다.

입력 지연을 두고 수행하는 가용성 검사는 전체 네임스페이스/저장소 경로를 사용합니다.
중복 로컬 키도 생성을 차단합니다. 조회 실패는 사용 가능 여부가 미확인임을 뜻하며,
키나 네임스페이스를 바꾸면 오래된 응답은 무시됩니다. 저장은 GitLab을 다시 확인하고
실제 생성 응답을 최종 판단 기준으로 삼습니다. 이전 검사가 성공한 뒤 생긴 경합도 포함합니다.

## 프로비저닝과 복구

Sync 서비스는 비동기 프로비저닝 전에 로컬 키를 예약하고 작업 영수증을
`.projects.env/.<key>.env`에 저장합니다. 저장소 생성, 템플릿 설치 및 CI 선택은
인스턴스의 GitLab Rails 어댑터를 통해 실행됩니다. 임시 범위 지정 API 자격 증명은
서버에만 유지되며 작업이 끝나면 폐기됩니다. GitLab 관리 자격 증명은 브라우저나
구성 내보내기로 전달되지 않습니다.

라우팅 적용 전에 저장소 식별 정보를 저장합니다. 따라서 재시도 시 다른 저장소를 만들지
않고 라우팅을 복구하거나 초기 파이프라인을 복구할 수 있습니다. 폴링은 인증된 짧은
요청으로 완료 상태나 안전한 오류를 반환합니다. 대기 중인 작업은 충돌하는 구성/서비스
변경을 차단합니다. 관련 없는 저장소, 편집된 관리형 파일 또는 불확실한 외부 결과는
영수증 초기화로 우회하지 말고 점검해야 합니다.

선택된 CI 경로는 `.system-bootstrapper/ci.yml`입니다. 업스트림 게시 파일은 별도로
보존됩니다. 환경 설정과 생성된 라우팅은 관리형 파이프라인과 일치해야 합니다.
프로젝트 프로비저닝 중에도 GitLab은 계속 실행됩니다.

## Wizard 자체 관리하기

Wizard를 활성화하고 구성한 상태에서 시작하면 비공개 `root/wizard` 시스템 프로젝트가
자동으로 등록됩니다. 이 프로젝트는 기존 인터페이스를 나타내며 운영 환경 호스트,
HTTP/HTTPS 모드 및 인증서 설정은 일반에서 가져옵니다. 반복 시작해도 저장소 식별 정보,
작업 흐름 영수증 및 설치된 선택적 환경 설정은 유지됩니다. 이미 사용 중인 로컬 키나
다른 소유자의 저장소는 덮어쓰지 않고 보고합니다.

등록 시 비활성 README/CI 골격이 생성됩니다. 이후 동작은 명시적이고 독립적입니다.

1. 커밋된 System Wizard gitlink에서 [소스를 초기화](WIZARD_SOURCE.md)합니다.
2. 가져온 애플리케이션과 불변 레지스트리 후보를 [빌드하고 검증](WIZARD_BUILD.md)합니다.
3. 별도 HTTPS 호스트에 [Review와 Beta](../project-bootstrap/wizard-environments/README.md)를
   구성하고 수동 GitLab 작업으로 배포/중지합니다.
4. 보호된 [운영 환경 승격 및 롤백 절차](../project-bootstrap/wizard-production/README.md)로
   검증된 후보를 적용합니다.

소스 가져오기, 후보 빌드 및 Review/Beta 배포는 실행 중인 관리 인터페이스를 교체하지 않습니다.
운영 환경 승격은 운영자 확인이 필요한 동작입니다. 소스를 가져와도 업스트림 저장소가
변경되거나 이 인스턴스가 개발 소스의 기준이 되지는 않습니다. 기본/백업 저장소 선택은
별도의 [구성 결정](GITLAB_GITHUB_BACKUP.md)입니다.

## 구성과 서비스 데이터

프로젝트 식별 정보와 작업 흐름 영수증은 인증된 가져오기, 백업/열기, 보내기 및 재시작
이후에도 유지됩니다. 관리형 Wizard 항목은 운영 환경 설정을 일반에 두고, 선택적
관리형 환경은 전용 대화 상자를 사용합니다. Harvest/Seed는 서비스 데이터와 인증서를
처리하며 구성 백업은 별도로 유지됩니다. 저장소 파일과 보존하는 빌드 증거에 비밀 정보를 넣지 마세요.
