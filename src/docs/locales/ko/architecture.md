# 아키텍처, 기원, 진화

System Bootstrapper는 저렴한 자체 호스팅 플랫폼에서 매번 서비스를 조립하지 않고 웹
프로젝트를 빌드하려는 작성자의 필요에서 2019년에 시작되었습니다. 아키텍처와 핵심 원칙은
AI 코딩 에이전트보다 먼저 만들어졌습니다. AI는 개발을 도울 수 있지만 아키텍처의 기원은 아닙니다.

**소스 코드는 DNA이며, 실행 중인 인프라는 그로부터 재구성할 수 있는 인스턴스입니다.**
인프라 정의는 소스에서 재현할 수 있습니다. 설치를 다시 구성하려면 저장된 구성, 비밀 정보,
데이터베이스와 저장소를 포함한 영구 서비스 데이터도 필요합니다.

플랫폼은 GitLab Community Edition, 해당 컨테이너 Registry, GitLab Runner 관리자,
NGINX 라우팅, 인증된 Sync API, React 구성 Wizard를 결합합니다. 셸 스크립트와 Docker
Compose가 이들의 수명 주기를 조정합니다.

## 운영 안내 지도

애플리케이션 스타터는 Angular, React, 일반 웹 프로젝트를 지원합니다.
[프로젝트 안내](PROJECT_BOOTSTRAP_GUIDE.md)는 비공개 저장소 생성, 편집 가능한 소스,
CI, 애플리케이션 환경을 설명합니다. Wizard 자체도 관리형 프로젝트로 등록됩니다.
명시적인 [소스 초기화](WIZARD_SOURCE.md), [빌드 구성](WIZARD_BUILD.md),
[Review/Beta 환경](../project-bootstrap/wizard-environments/README.md),
[제어된 운영 환경 승격](../project-bootstrap/wizard-production/README.md)은 각각 검사 가능한
별도 작업입니다. 소스를 빌드하거나 병합하는 것만으로 실행 중인 관리 인터페이스가 교체되지는
않습니다.

기존 Wizard 개발 저장소를 가진 운영자는 대신
[하나의 소스 우선 Wizard 프로젝트](../project-bootstrap/wizard-source-primary/README.md)를
소스, 기본 검사, 후보 환경, 프로덕션 이미지에 채택할 수 있습니다. 사용자 변경 위로 소스를
가져오지 않으면서 개발과 전달을 하나의 저장소에서 유지합니다. 다른 설정을 위해 레거시
관리형 초기화도 계속 사용할 수 있습니다.

운영자는 선택적인 [GitHub 코드 미러](GITLAB_GITHUB_BACKUP.md)와 함께 GitLab을 개발 및
이슈 추적 플랫폼으로 선택할 수도 있습니다. 해당 안내는 소스 이력 매핑, 검토된 병합,
트래커 마이그레이션, 검증을 다룹니다. 미러는 병합된 코드를 전달하고, 선택한 라이브 저장소와
복구 계약이 GitLab 서비스 상태를 보존합니다.

번들 System/Wizard 변경에서는 선택적인 [System 후보 Review 작업](SYSTEM_CANDIDATE_REVIEW.md)이
테스트된 Wizard 이미지를 구성된 Review HTTPS 호스트에 재사용하여, 명시적인 운영 환경
승격 전에 개인 UI 승인 검사를 할 수 있습니다.

영구 서비스 데이터는 `PERSISTENT_DIR` 아래에 있습니다. 일반적으로 Ubuntu/WSL 시스템
디스크의 `/var/lib/system-bootstrapper/platform`입니다. 플랫폼 시작이나 운영에 두 번째
디스크나 백업 매체는 필요하지 않습니다. 명시적인 볼륨 기반 라이브 레이아웃도 지원하며,
볼륨이 없을 때 대체 저장소로 전환하지 않습니다. Wizard는 구성을 별도로 내보냅니다.
[Harvest/Seed](RECOVERY_CONTRACT.md)는 독립적으로 선택한 백업 저장소에 완료된 서비스
데이터 스냅샷을 만들고 복원합니다. VM을 삭제하면 로컬 작업 데이터도 삭제됩니다. 복구에
의존하기 전에 완료된 외부 Seed와 일치하는 구성을 보존하세요. 보존된 라이브 데이터
파일시스템은 Seed 복원 없이 재사용할 수도 있습니다.

2026년 11월 7일, Seed 없는 새 공개 릴리스 설치에는 **10분 58초**가 걸렸고, 외부 Seed에서
새 로컬 작업 저장소로 복구하는 데는 **16분 22초**가 걸렸습니다. 운영자 지원하에 관찰된
이 시간은 검증 범위가 서로 다르며 시간 보장이나 직접적인 성능 비교가 아닙니다. 하드웨어,
사전 조건, 측정 시작과 끝의 기준은
[측정 맥락과 반복 가능한 절차](HANDBOOK.md#measured-installation-and-recovery-times)를 참조하세요.

저장소에는 [컴포넌트 및 통합 검사](../tests/README.md)가 제공됩니다. 후보 하네스는 격리된
자원으로 폐기 가능한 플랫폼 인스턴스를 실행합니다.
[진화 장](HANDBOOK.md#5-evolving-a-running-system)은 기존 상태 마이그레이션과 복구를
포함하여 지원되는 후속 버전을 개발, 검증, 명시적으로 승격하는 전체 절차를 설명합니다.

## 이 프로젝트가 존재하는 이유

개발 플랫폼 설정에는 GitLab을 설치하거나 컨테이너 몇 개를 시작하는 것보다 많은 일이
필요합니다. GitLab, Runner, Registry, 애플리케이션 환경, 네트워크, 도메인, 리버스 프록시가
함께 작동해야 합니다.

System Bootstrapper는 이 설정을 저장소에 담습니다. Docker 컨테이너가 서비스를 제공하고,
스크립트와 구성이 이들을 개발 플랫폼으로 연결합니다. 의도된 시작점은 필요한 접근 권한과
자원을 가진 Ubuntu 호스트입니다. 부트스트랩 과정은 최소한의 수동 설정으로 이 호스트를
사용 가능한 환경으로 바꾸어야 합니다.

하지만 설치는 시작일 뿐입니다. 의존성이 바뀌고 서비스가 진화하면 한때 잘 작동하던 환경도
업데이트하기 어려워질 수 있습니다. 이 갱신을 일상적이고 테스트 가능한 개발 절차로 만드는
것이 프로젝트의 핵심 목적입니다.

## 자체 도구로 플랫폼 진화시키기

실행 중인 세대 **A**가 세대 **B**를 위한 개발 플랫폼을 제공합니다. 이는 Wizard뿐 아니라
컨트롤러와 지원되는 GitLab/Runner 전환을 포함한 인프라 자체에도 적용됩니다. 초기화, 검증,
승격, 복구 도구가 저장소에 있으므로 다른 운영자도 자체 인프라와 입력으로 같은 절차를
사용할 수 있습니다.

절차는 다음과 같습니다.

1. **A를 사용해 B를 개발합니다.** 브랜치와 GitLab 병합 요청으로 플랫폼 소스, 이미지 고정,
   도구에 대한 변경을 제안합니다.
2. **후보를 빌드하고 테스트합니다.** CI가 커밋된 소스를 검사하고 완전한 후보 이미지를
   빌드합니다. 런타임 변경에는 컴포넌트 검사와 폐기 가능한 격리 플랫폼 테스트가 필요합니다.
   문서 전용 변경은 짧은 문서 경로를 사용합니다.
3. **지원되는 전환을 검증합니다.** 업그레이드에서는 대표적인 기존 서비스 데이터, 필수
   마이그레이션, Runner/Registry 동작, 복구를 테스트합니다. 빈 후보를 시작하는 것만으로는
   업그레이드 안전성을 입증할 수 없습니다.
4. **검토하고 병합합니다.** 필수 게이트를 활성화된 상태로 유지합니다. 병합된 기본 브랜치
   리비전은 해당 검사를 별도로 받습니다. 병합이 운영 환경을 자동으로 교체하지는 않습니다.
5. **승인된 버전을 승격합니다.** 커밋된
   [컨트롤러 승격 도구](../bootstrapper/README.md#promoting-a-tested-successor-controller)와,
   선언된 GitLab 마이그레이션에 해당하는
   [업그레이드 절차](HANDBOOK.md#migrate-gitlab-through-the-accepted-controller)를 사용합니다.
   이들은 작업을 승인된 소스/이미지 증거에 연결하고 체크포인트와 복구 작업을 보존합니다.
6. **다음 주기를 위해 B를 준비합니다.** 실행 중인 서비스를 검증하고
   [일치하는 복구 입력](HANDBOOK.md#export-bs-matching-recovery-inputs)을 내보내며 승인된
   소스와 이미지를 보관합니다. 그러면 B가 다음 검토된 변경을 위한 개발 플랫폼과 도구를 제공합니다.

이 작업들은 의도적으로 분리되어 있습니다. 컨트롤러 승격 자체는 GitLab 데이터베이스를
마이그레이션하지 않습니다. 단일 노드 GitLab 업그레이드에는 중단 시간이 있고 복구에 호환되는
콜드 체크포인트를 사용합니다. NGINX 대상을 바꾸거나 이미지를 되돌려도 데이터베이스
마이그레이션은 취소되지 않습니다. GitLab을 사용할 수 없는 동안에도 승인된 체크아웃, 이미지,
자격 증명, 복구 입력에 업그레이드 대상 서비스와 독립적으로 접근할 수 있어야 합니다.

[선언된 릴리스 프로필](../gitlab/security-release.json)과 테스트가 지원되는 마이그레이션을
정의합니다. 새 버전이나 컴포넌트 변경에는 여전히 자체 승인 기준과 성공한 검사가 필요합니다.
기존 도구가 모든 가능한 업그레이드의 안전성을 보장하지는 않습니다.

## 비전: 자동화된 재귀적 자기 개선

다음 단계는 개발자 주도의 갱신을, 개선점을 식별하고 변경을 제안하며 명시적 목표에 비추어
평가한 뒤 개선된 시스템에서 반복하는 피드백 루프로 확장하는 것입니다. 이 단계를 수행하는
장치 자체도 진화할 수 있습니다. 한 세대를 다시 빌드하거나 교체하는 것만으로는 개선되었다고
입증할 수 없습니다.

AI 에이전트는 같은 절차로 개발과 검토를 도울 수 있습니다. 임의의 개선을 자동으로 선택하고
재귀적으로 승격하는 자율 기능은 구현되어 있지 않습니다. 현재 도구는 한정된 작업을
자동화하며, 자체 목표를 선택하거나 자신에게 운영 환경 승인을 부여하지 않습니다.

System Cube는 모듈식 통신의 이론적 가능성도 기록합니다. ASCII 서명의 `$` 구멍은
포트 `8071`에 반영되어 있으며, Seed를 도입하고 다른 Bootstrapper 인스턴스와 통신하기 위한 미래의 외부
연결구를 상징합니다. 의도된 모델에서 각 시스템은 주변에 인터페이스를 노출하고 서로 통신하는
다른 시스템을 내부에 포함하여 재귀적으로 구성할 수 있습니다.

현재 Sync API는 이 광범위한 통신 모델을 구현하지 않습니다. Bootstrapper 간 통신과
중첩된 모듈식 구성은 아직 명세와 실증이 필요합니다. 포트 `8071`에서 수신 대기하는 것만으로
해당 프로토콜이 성립하지는 않습니다.

## 하나의 호스트, 여러 플랫폼 세대

후보마다 별도의 VM이 필요한 것은 아닙니다. 충분한 자원을 갖춘 호스트에서는 폐기 가능한
플랫폼 하네스를 운영 환경과 함께 실행하면서 Docker 데몬, 컨테이너, 네트워크, 상태를
분리할 수 있습니다. 후보 인스턴스는 테스트 동안만 존재하고 이후 제거됩니다. 영구적인 두 번째
플랫폼은 필요하지 않습니다.

애플리케이션 Review/Beta 환경은 진입점 NGINX 서비스와 별도의 운영 환경, Beta,
Review 프록시를 사용하며 `VIRTUAL_HOST`로 애플리케이션을 동적으로 라우팅합니다.
이 환경들은 전체 플랫폼 후보 하네스와 별개입니다. 후보 테스트 통과가 후속 플랫폼 전체를
운영 환경으로 자동 라우팅하지는 않습니다. 지원되는 각 승격은 선언된 마이그레이션과 복구
절차를 따릅니다.

단일 호스트는 인프라 규모를 작게 유지하지만 여전히 자원과 장애 영역을 공유합니다. 컨테이너는
호스트 커널을 공유하며 독립된 가상 머신이 아닙니다. 호스트 수준의 Ubuntu, 커널, Docker
Engine 업데이트에는 자체 유지 관리 경로가 필요합니다.

## 성공적인 갱신이 입증해야 할 사항

컨테이너가 시작된다는 이유만으로 후보가 준비된 것은 아닙니다.
[플랫폼 및 마이그레이션 검사](HANDBOOK.md#53-validate-existing-state-migration-not-only-first-startup)는
선언된 변경에 필요한 동작을 입증해야 합니다.

- GitLab에 접근할 수 있고 플랫폼 저장소를 호스팅할 수 있어야 합니다.
- Runner가 파이프라인을 실행하고 이미지를 빌드할 수 있어야 합니다.
- Registry가 해당 이미지를 받아들이고 제공할 수 있어야 합니다.
- 도메인 라우팅이 올바른 환경에 도달해야 합니다.
- 후보 환경이 운영 환경과 공존하고, 영향을 주지 않고 제거될 수 있어야 합니다.
- 빈 설치뿐 아니라 대표적인 기존 데이터에서도 업그레이드가 작동해야 합니다.
- 실패한 배포에 테스트된 복구 경로가 있어야 합니다.

컨테이너 정의는 재현할 수 있지만 GitLab 저장소, 데이터베이스 내용, Registry 데이터, 구성,
비밀 정보에는 여전히 의도적인 영구 저장과 보호가 필요합니다. 이미지 업데이트만으로 안전한
마이그레이션을 보장할 수 없고, 이미지를 되돌려도 데이터베이스 마이그레이션이 되돌아가지 않을
수 있습니다.

## 저장소 지도

| 경로 | 기존 구현에서의 목적 |
| --- | --- |
| `start.sh`, `stop.sh` | 최상위 수명 주기 진입점입니다. |
| `bootstrapper/` | 기반 이미지, 호스트 초기화, 복구, 런타임 검증, 승인된 컨트롤러 승격/내보내기 도구입니다. |
| `system/` | 기본 Compose 정의와 오케스트레이션 스크립트입니다. |
| `gitlab/` | GitLab 수명 주기/구성과 지원되는 업그레이드, 체크포인트, 롤백 도구입니다. |
| `gitlab-runner/` | Runner 구성, 등록, 수명 주기 스크립트입니다. |
| `nginx/` | 진입점 리버스 프록시 구성과 수명 주기 스크립트입니다. |
| `nginx-proxy/` | 운영 환경, Beta, Review 프록시 구성입니다. |
| `sync/` | 동기화 관련 구성과 스크립트입니다. |
| `wizard/` | 구성 Wizard 서브모듈입니다. |
| `.gitlab-ci.yml` | 짧은 문서 경로, 필수 런타임 컴포넌트/이미지/폐기 가능한 플랫폼 검사, 이미지 게시, 선택적 GitHub 미러입니다. |
| [tests/](../tests/README.md) | 컴포넌트 목록, 격리 테스트 명령, 명시적인 라이브 통합 경계입니다. |
| [Prepare-Host.md](../Prepare-Host.md) | 호스트 설치, 서비스 이미지 선택, 시작입니다. |

## 배포 빌드 및 검증

[핸드북](HANDBOOK.md)에서 로컬 또는 공개 서버 설치 경로를 고르고,
[호스트 준비](../Prepare-Host.md)에 따라 설치하세요. 서비스 버전을 선택하고 영구 저장소를
명시적으로 구성하세요. [복구 계약](RECOVERY_CONTRACT.md)은 구성과 Seed를 함께 복원하는
방법을, [영구 저장 안내](PERSISTENT_VOLUME.md)는 보존된 라이브 데이터의 재사용을 설명합니다.

복원과 후보 테스트에는 폐기 가능한 환경을 사용하세요. Bootstrapper는 Docker 소켓을
마운트하며 호스트의 서비스, 네트워크, 포트, 영구 볼륨을 변경할 수 있습니다. 문서화된
[검증 명령](../tests/README.md)을 실행하고 결과를 검사한 뒤 이미지를 승격하세요. 호스트
OS/커널 유지 관리와 GitLab 주 버전 데이터베이스 업그레이드에는 각각 자체 절차가 있습니다.

## 기본 원칙

**안정된 각 세대는 다음 세대를 빌드하고 테스트하고 전달할 도구를 제공해야 합니다.**
자체 진화도 사용자에게 제공하는 것과 같은 검토 가능한 소프트웨어 엔지니어링 절차를 따릅니다.
