## 측정된 설치 및 복구 시간

**2026년 11월 7일** 운영자 지원하에 수행한 두 번의 실행은 각 호스트에서 Ubuntu
**26.04.1 AMD64**, **8 vCPU**, 약 **32 GB RAM** 및 **225 GB 시스템 디스크**를
사용했습니다. 둘 다 GitLab **19.5.3**, **Runner 관리자 4개**, System 소스 리비전
`c12a00cebe27b5d7601052448480c12494b95c19`와 고정된 Wizard 하위 모듈을 사용했습니다.
라이브 서비스 데이터는 시스템 디스크에서 `PERSISTENCE_MODE=local`을 사용했습니다.

| 시나리오 | 첫 SSH 명령(UTC) | 준비 완료 검증(UTC) | 소요 시간 |
| --- | --- | --- | --- |
| Seed나 외부 디스크 없는 새 설치 | 18:39:13.884 | 18:50:12.231 | **10분 58초** (658.347초) |
| 외부 Seed를 새 로컬 작업 저장소에 복원 | 18:57:12.746 | 19:13:35.166 | **16분 22초** (982.420초) |

새 설치에서는 도메인과 Runner 수 설정만 재사용했습니다. 이전 데이터베이스, 서비스
데이터, 프로젝트 또는 기존 인스턴스 자격 증명은 없었습니다. 신뢰할 수 있는 인증서를
새로 발급했습니다. 전체 컨트롤러와 일치하는 Wizard는 호스트에서 빌드하지 않고 검증된
공개 릴리스 이미지에서 가져왔습니다.

복구에서는 일치하는 별도 저장 Wizard 구성을 사용하여 약 **3.1 GB의 Seed 페이로드**를
빈 내부 작업 저장소에 복사하고 검증했습니다. Seed는 GitLab 데이터베이스, 저장소,
레지스트리, 비밀 정보 및 인증서/갱신 상태를 보존했습니다. 저장된 컨트롤러 선택자는
의도적으로 승인된 공개 릴리스로 변경했으며, 다른 설정과 자격 증명은 보존했습니다.
정확한 기존 비공개 Wizard와 선택적인 과거 CI 도우미 이미지는 복원된 레지스트리에서
복구했습니다. 이러한 이미지의 별도 아카이브나 호스트 빌드는 사용하지 않았습니다.
플랫폼 시작 전에 백업 저장소를 마운트 해제했습니다.

이들은 서로 다른 세 가지 저장소 작업 흐름입니다.

- **새 초기화:** 로컬 작업 저장소에 새 서비스 상태를 만듭니다. Seed나 외부 매체가 필요하지 않습니다.
- **Seed 복구:** 완료된 백업을 검증하여 새 작업 저장소에 복사하고 그 로컬 사본에서 실행합니다.
  일반 작업, 구성 변경 및 인증서 갱신에는 연결된 백업 매체가 필요하지 않습니다.
- **기존 라이브 볼륨 재사용:** 기존 라이브 데이터 파일시스템을 연결하고 Seed를 복사하지 않고
  재개합니다. 이 별도의 교체 호스트 절차는 이번 실행에서 **측정하지 않았습니다**.

Harvest/Seed는 서비스 데이터를 위해 별도로 선택한 백업 저장소를 사용합니다.
Wizard 열기/백업과 Sync 보내기/가져오기는 구성을 독립적으로 관리합니다. Seed는 일치하는
구성 백업을 대체하지 않습니다. [저장소 가이드](PERSISTENT_VOLUME.md)와
[복구 계약](RECOVERY_CONTRACT.md)을 확인하세요.

### 측정 범위와 준비 상태

UTC 타임스탬프와 경과 초를 사용하여 첫 SSH 명령부터 선언된 준비 완료 시점까지
측정했습니다. 측정 전 각 실행에는 이미 프로비저닝된 VM, 해당 주소와 DNS, SSH 권한,
인터넷 접속 및 운영자의 구성 입력값이 준비되어 있었습니다. 복구에는 추가로 연결된
완료 Seed와 일치하는 구성 백업이 있었습니다. VM 프로비저닝, DNS 전파 및 SSH 키
프로비저닝은 제외했습니다.

포함된 작업은 호스트 사전 요구사항과 Docker 설치, 체크아웃 및 하위 모듈 설정,
이미지 가져오기, 구성, 서비스 시작, 인증서 통합 및 갱신 검증입니다. 실행 중 운영자
준비, 대기 및 검사 재시도도 측정 시간에 포함했습니다. 새 설치에서는 Runner의 최근
접속 확인을 처음에 재시도했고, 복구에서는 메타데이터 검사를 재시도했습니다.
이들은 운영자가 지켜보며 진행한 절차이며 무인 설치 프로그램의 측정치가 아닙니다.

새 설치의 준비 완료 조건은 신뢰된 공개 Wizard, GitLab 및 레지스트리 응답, 인증된
유휴 Sync, 성공적인 시험 실행을 포함한 인증서 갱신 설정 완료, 현재 Runner 관리자
4개 모두의 GitLab 온라인 확인이었습니다. 복구에는 보존 상태 검사, 정확한 과거 CI
도우미 복구 및 임시 레지스트리 자격 증명 폐기가 추가로 필요했습니다. 해당 실행에서
공개 경로와 인증된 Sync는 약 **13분 20초**에 이미 통과했고, 추가 복구 검사는
**16분 22초**에 완료되었습니다. 과거 Runner 관리자 기록만으로 현재 관리자로
인정하지 않았습니다.

이후 이미지/저장소 및 최종 정리 검사를 포함한 준비 완료 후 감사는 소요 시간에서
제외했습니다. 두 실행 모두 별도의 전체 시스템 테스트 파이프라인을 시작하지 않았습니다.
당시의 준비 상태 범위는 표준 Wizard 별칭 리디렉션을 확인하지 않았습니다. 배포에
필요하면 명시적으로 포함하세요. 이 관찰로 모든 애플리케이션 또는 CI 워크로드가
테스트되었다고 볼 수는 없습니다.

두 실행은 수행 작업과 검사가 달랐으므로 통제된 A/B 벤치마크나 직접적인 성능 비교가
아닙니다. 호스트 성능, 네트워크 및 이미지 캐시, 레지스트리 가용성, 인증서 발급,
운영자 상호작용, 데이터 크기 및 선택한 승인 검사가 모두 소요 시간에 영향을 줍니다.
이 값은 관찰 결과이며 설치 시간을 보장하지 않습니다.

### 자신의 입력값으로 측정 반복하기

1. 호스트 OS/아키텍처, CPU, RAM, 디스크와 저장 모드, 승인된 소스 및 이미지 다이제스트,
   GitLab 버전과 원하는 Runner 관리자 수를 기록하세요. 자신의 도메인, DNS, SSH 접속,
   방화벽 규칙 및 비공개 구성을 제공하세요. 복구 시 완료된 Seed의 페이로드 크기와
   식별 정보도 기록하고 별도의 구성 백업이 일치하는지 확인하세요. 빈 라이브 대상을
   선택하세요. 새 설치 시간을 재려고 실행 중인 설치를 덮어쓰지 마세요.
2. 시작 전에 필수 검사를 정하세요. 한 관리 컴퓨터에서 UTC를 기록하고 첫 SSH 명령
   직전에 단조 시계 기반 스톱워치를 시작하세요. 시도 중 해결한 실패를 포함하여
   운영자 입력, 대기 및 재시도 내내 계속 측정하세요. 각 이정표의 UTC와 경과 시간을
   비공개로 기록하고 검사 실패 후 시계를 초기화하지 마세요.
3. 새 초기화는 검토된 릴리스 체크아웃의 `bootstrapper/install.sh`,
   `bootstrapper/install-release.py` 및 `bootstrapper/install-volume-host.sh`를
   사용하여 [공개 HTTPS 안내](#public-server-own-domain-and-https)를 따르세요.
   릴리스의 불변 컨트롤러와 이에 맞는 Wizard 이미지를 선택하세요. Wizard 가져오기,
   백업 및 보내기로 구성하고 이번 실행의 수를 재현하려면 관리자를 4개로 설정하세요.
   최초 인증서 발급과 `system-certbot`을 사용하는 문서화된 webroot 갱신/deploy-hook
   검사를 완료하세요.
4. [외부 Seed 복원](RECOVERY_CONTRACT.md#restore-an-external-seed-into-a-fresh-local-installation)을
   따르세요. 네이티브 저장소 준비와 실제 복원 전
   `bootstrapper/seed-operation.sh restore --check-only`를 포함하며 일치하는 구성
   백업을 사용해야 합니다. 복원 검증이 끝날 때까지 GitLab을 중지해 두세요. 이번 실행의
   저장소 분리를 재현하려면 도우미 완료 후 시작 전에 백업 매체를 마운트 해제하세요.
   호스트 인증서 통합을 설치하고 `start.sh`로 시작하세요.
   [네이티브 비공개 Wizard 복구](RECOVERY_CONTRACT.md#pulling-a-restored-private-wizard-image)는
   저장된 다이제스트를 유지하고 범위가 지정된 임시 레지스트리 접속을 정리합니다.
5. 신뢰된 TLS로 공개 Wizard, GitLab 및 레지스트리를 확인하고 인증된 Sync 가져오기와
   유휴 상태, 인증서 갱신/배포 및 GitLab에서 현재 관리자 모두의 온라인 상태를 확인하세요.
   안내에 라우팅과 갱신 명령이 있으며 [Runner 설정](#2-setting-up-gitlab-runners)은
   공유 풀과 관리자 식별 정보를 설명합니다. 복구에서는 보존된 저장소, 레지스트리 내용
   및 예상 저장 설정도 확인하세요. 추가 관리형 이미지 또는 애플리케이션 검사를 정하고
   해당 복구와 임시 자격 증명 정리를 준비 완료 범위에 포함하세요.
   [네이티브 런타임 검증기](../bootstrapper/README.md#reviewed-replacement-host-initialization)를
   사용하는 흐름에서는 최근 관리자 접속 확인용 비공개 API 토큰 파일을 제공하고,
   표준 Wizard 별칭이 필요할 때는 `--redirect-from`을 제공하세요. 건너뛴 검사는
   계속 건너뛴 것으로 표시해야 합니다.
6. 마지막 필수 검사가 성공하면 준비 완료 UTC와 경과 초를 기록하고 스톱워치를 멈추세요.
   이후 감사와 정리는 별도로 기록하세요. 자격 증명, 구성 내보내기, 머신 주소 및 원시
   로그는 비공개 운영자 기록에 보관하세요. 민감 정보를 제거한 맥락, 측정 범위 및 결과만
   게시하세요. 실패하거나 중단된 시도는 별도의 결과이며 성공 소요 시간에서 빼버릴
   구간이 아닙니다.
